1. Executive Summary

ARTEX is a self-hosted penetration-testing platform in Go on PostgreSQL. A planner splits a goal into intents, workers run tools, and results are written into two graphs: a global asset graph and a per-task exploration graph. This report covers only what the system remembers across turns and tasks.

It carries trust_state, scope_enforced, audit_log and negative_eval. audit_log sits on the coverage ledger alone.

Licence and provenance. LICENSE is the unmodified AGPL-3.0 text. The README then adds permitted and prohibited uses, calls them additional terms from the maintainers, and says use of the project means agreement (README.md:1006-1041); code review and academic research are listed as permitted. web/ is MIT, a third party's UI template. The README describes the repository as the maintained community continuation of a project whose original repository is no longer public (README.md:982), and its history holds the original author's commits to 7 October 2026. The Go module path and the agent SDK dependency carry the original owner's name, and the SDK was not opened for this reading.

Cross-task memory has three forms, and the oldest is the soundest.

  • Inheritance. A task may name up to eight source tasks. Its agents then read the sources' facts, findings and finished intents, tagged as inherited, through one hop of live relations (db/exploration_sources.go:16-41). Graph writes cannot cross: every node mutation carries the receiving task's exploration_id.
  • The asset graph. One table for the installation. An agent inside a task sees only assets matched by the scope rows of that task and its sources (db/task_assets_context.go:65-90).
  • Lessons. A rule turns each triaged finding into one line of text for later tasks (db/lessons.go:158-309). No model writes it. Injection is off unless ARTEX_RSI_LESSONS=inject.

A lesson follows the verdict behind it, in the verdict's transaction. Each lesson holds evidence rows naming the finding or retest it came from. A disposition change runs the extraction before it commits. The extraction marks that finding's rows withdrawn on lessons of the opposite kind and sets a lesson with no live row to retired, which the selection excludes (db/notification.go:503-520, db/lessons.go:337-357, :403-417, :448). Withdrawn rows stay, one per withdrawal, so a retired lesson names what it rested on and when each support was lost.

A false-positive verdict stops goal proof and undoes it. The disposition is copied into the finding node's payload in the same transaction, every finding list an agent reads carries it, and prove_goal refuses a finding marked false_positive, duplicate or ignored (agent/tools.go:1453-1458). Writing one of those statuses also sets a goal the finding had proved back to open, unless another valid proof remains (db/notification.go:590-625).

A fact needs recorded work behind it. The server looks for a fact's evidence line in the recorded activity of its intent and stores the result as provenance. A fact it cannot tie is unverified and proves no goal. One source is taken on the agent's word: a fact declared operator_input is not checked.

The scope rows belong to the reader. The planner holds add_task_scope, which writes a company, domain or address row into its own task's scope. The asset query and the lesson selection both follow every row of the task, whoever wrote it.

A model can decline a finding before it is stored. When the operator names a decision-model profile, report_finding first asks that model whether the candidate repeats a registered finding. A confident yes returns the matched ids and writes nothing. The caller can repeat the call with force_register. The check is off until the profile is set, and every failure registers the finding as before.

2. Mental Model

A lesson is a triaged finding restated by rule, kept while its evidence stands.

3. Architecture

A Go server, a PostgreSQL schema of 57 tables in one idempotent file with fourteen numbered migrations beside it, an agent package (planner, worker, main agent, retester, compactor) on an external SDK, and a Next.js UI. There is one operator: a single JWT subject, bound to a password version, guards every API route but the auth routes and the health and readiness probes (server/auth.go:188-203, :332-340). There is no user or tenant table.

Docker Compose with PostgreSQL, or a single binary with the UI embedded. The lessons flag appears in RSI.md and docs/rsi-lessons.md and in no README, example environment file or UI.

5. Memory Data Model

Asset. One row per domain, IP, subdomain, app, service or endpoint, unique on its value with no task or company in the key (db/schema.sql:84-92). It carries task_ids, a company, and three record times: created_at, last_seen, updated_at.

Exploration node. kind is one of begin, goal, intent, fact, finding, hint, digest, with a JSON payload, a state and an origin stamped by the server from the calling agent. Edges are spawns, derived_from, yields, proves, covers. An anchor row links a node to an asset.

Fact. A summary, a detail, a one-line evidence string, a confidence of observed or inferred, and a source from a fixed list that includes target_response, tool_output, operator_input and inference (agent/tools.go:1662-1673). The agent declares both. The server adds a provenance: recorded_activity when the evidence line appears verbatim in the recorded activity of the fact's intent, captured_traffic when the same bytes also came back through the capture proxy, operator_input, or unverified (:1675-1684, :1737-1764). An unverified fact is stored with its source lowered to inference and its confidence to inferred, and a captured one is relabelled target_response whatever the agent wrote (:1812-1824).

Finding. A node plus a findings row whose status starts at pending (db/schema.sql:1205) and is the person's disposition: confirmed, false_positive, duplicate, ignored, risk_accepted and others. A second column, report_state, tracks the report stage after triage and feeds no lesson. Evidence binds a finding to content-addressed snapshots of captured requests and responses.

Scope row. A task_scope row is a company, root domain, subdomain, address, range, registration number or keyword (db/schema.sql:783-784), with a source of auto, agent or manual. An agent's addition that widens a declared scope is stored with expanded set (db/task_scope.go:225-233). A line written *.example.com is stored as the example.com domain rule, and a wildcard on anything but a registrable domain is refused (db/company_scope.go:256-263).

Lesson. kind (positive, negative, caution), cue, action, optional category and company, a status, and a dedupe_key that is a hash of kind, scope, cue and action. Support is not stored; it is the count of evidence rows with no withdrawn_at, taken at read time. A partial unique index allows one live row per lesson and source and any number of withdrawn ones (db/schema.sql:1568-1579). The status column accepts candidate, adopted and retired. Product code writes retired and returns a row to candidate; adopted appears only in the CHECK constraint and in tests that set it with SQL (db/schema.sql:1557-1558).

The company comes from the task's task_scope rows of kind company. A task with exactly one gets that id on its lessons, and a task with none gets NULL (db/lessons.go:125-130). A task declared by domain alone has no company.

No field records when something about a target was true, as distinct from when it was written. bitemporal is withheld.

6. Retrieval Mechanics

The planner's view of its own task

graphOverviewData is injected into every planner round as windows over the graph, each newest first: thirty open intents, twelve recent finished ones, ten findings, twenty facts not folded into a digest, fifteen digests (agent/tools.go:493-732). Each finding in the window carries its triage status, and findings_total counts the findings not marked false_positive, duplicate or ignored (:593, :618-623). The rest stay reachable. list_facts pages by cursor, list_findings lists up to 500, and a folded region opens with expand_digest.

After the overview comes a block naming up to ten finished intents that yielded facts and no finding, newest first, each with its fact count and 140 characters of its summary inside the nonce frame (db/exploration.go:1235-1266, agent/planner.go:418-453). It asks the planner to register each as a finding or say why it is not one.

Other tasks

…WithSources readers append the direct source tasks' nodes, tagged with the source task id. An inherited intent is visible only once it is terminal, so a running source task's in-flight work never enters another task's frontier (db/exploration_sources.go:74-81). The overview's share for related tasks is capped at 48,000 runes, 8,000 per source (agent/tools.go:742-743).

Assets

list_assets inside a task goes through scopeTargetCTE: the task and its direct sources, joined to their scope rows by company, root domain, subdomain, IP range or registration number, and the query adds id IN (SELECT id FROM target) (db/asset_dsl.go:622). Membership is by scope row, not by which task produced the asset, and the join takes every row whatever its source. With no task id, the platform and chat agents get the unscoped query (:598-600).

The operator's asset list takes a company id, and QueryDSLForCompany appends company_id = $n outside the compiled expression (db/asset_dsl.go:543-569). No agent tool calls it.

The query language compiles a disjunction inside one pair of parentheses, so the scope clause appended with AND binds the whole expression (db/asset_dsl.go:305-309). Until 84a623bf… on 20 November 2026 it did not: a OR b compiled to (a) OR (b) AND id IN (…), and the first branch returned assets from the whole installation. v0.6.0 is on the unparenthesised side of that commit.

No read filters on last_seen; it orders results only.

Lessons

One query (db/lessons.go:435-458). It keeps rows that are not retired, whose category is NULL or the task's, and whose company is one of the task's. A row with no company is kept only for a task that has no company either (:449-452). It orders company matches first, then category matches, then positive before negative before caution, then live support, with LIMIT 8 for injection and 50 for the HTTP preview. Both scope terms are written col IS NOT NULL AND col = …, so a NULL never sorts ahead of a match.

On a scratch PostgreSQL with the lifted DDL and query, a store of five lessons of one company, three of a second and four with none returned five to a task of the first company, four to a company-less task, and eight to a task holding both companies.

Rendering stops at the first entry that would pass 1,800 characters (db/lessons.go:564-566). A cue may run to 160 characters and an action to 320, so three full-length lessons fill the block and a long early entry hides shorter later ones. The function returns the ids it rendered, and those are what the usage log records (server/lessons.go:55-65). The block is fixed when the task's agents are built.

7. Write Mechanics

Facts, findings, coverage

Workers call record_fact, report_finding and record_coverage. A fact is created confirmed with its origin stamped by the server and its provenance computed before the node is written (agent/tools.go:1784-1854); no tool or route edits or deletes one. A fact's asset anchors must name existing assets, checked under a row lock before the node is created. A coverage write that exceeds a field limit is refused instead of truncated (db/coverage_ledger.go:41-52).

The duplicate check on report_finding

A setting names a model profile that serves a closed-list decision endpoint (server/triage.go:24-42). It is empty by default, and the worker and planner are then built with no client. With one, report_finding assembles a candidate pool before it stores anything (agent/triage.go:324-375):

  • the task's findings and those of its direct source tasks, up to 500;
  • findings of any other task anchored to one of the candidate's asset ids, newest ten, with no task relation, scope row or company in the query (db/finding_dedup_pool.go:25-71).

The pool is cut to ten by vulnerability class, a shared endpoint token and recency (:436-480). The model is sent the candidate and the ten, each with class, severity, name and 400 characters of summary, and answers with one id or none. An id it was not offered counts as none.

A match at or above the threshold, 0.5 unless the operator's setting changes it, ends the call. The tool returns the matched finding's two ids and the confidence, and the candidate's summary, evidence and traffic references are written nowhere. A log line is the only trace (agent/tools.go:1576-1601). No client, an empty pool, a transport error, a status other than 200 and a low confidence all fall through to the normal write.

Three properties of the path:

  • The writer overrides the verdict. force_register on a second call skips the check, and the tool description advertises it. The suppressed agent and the overriding agent are the same agent.
  • The pool ignores triage status. No query or filter on the path reads a finding's status, so a finding marked false_positive is offered as a duplicate target like any other. A report absorbed into it is dropped with no row for a person to review.
  • The advice names a tool the caller lacks by default. The answer tells the agent to extend the matched finding with update_finding_report. That tool is bound to the reporter and Auto agents (server/orchestration.go:528-539, :908-913), and its write is keyed on the node id with no task check (:446-449, db/finding_traffic.go:700). For a match from the cross-task pool, the id handed back belongs to another task.

Assets

Eight upsert functions. On conflict the last non-null writer wins per scalar column and arrays are unioned (db/assets.go:773-797). When two tasks disagree about a status code or a page title, the later one replaces the earlier and nothing keeps the old value.

Scope rows

Task creation writes the company rows the operator chose. After that the rows have three writers: the operator's route, the automatic row for each host a worker inserts, and add_task_scope, which the planner and the operator's chat agent hold (agent/tools.go:2591, agent/tools_insert.go:739). The tool accepts every kind, including company by name or id, and its description calls the result a coverage scope that is not enforced (agent/tools_insert.go:462-476).

Lessons

ExtractLessonsForTask reads each finding of the task with its newest completed retest and applies four rules (db/lessons.go:252-306):

  • confirmed, resolved or fixed gives a positive lesson, and a second one when that retest reproduced it.
  • A retest verdict of fixed or inconclusive on such a finding gives a caution.
  • false_positive, duplicate, ignored or risk_accepted gives a negative lesson that begins Do not re-report without new mechanics and ends with the status.
  • pending and in_progress give nothing and withdraw nothing.

The first and third rules also withdraw. A positive disposition marks the finding's evidence withdrawn on negative lessons. A negative one marks it withdrawn on positive lessons, on cautions, on every retest of the finding, and on any negative lesson whose action differs from the one being written (:271, :289-303). A lesson left with no live evidence is set to retired, and an upsert that meets a retired row with no live evidence sets it back to candidate (:403-417, :316-326).

Restoring support inserts a row. The insert conflicts only with a live row for the same lesson and source, so a finding confirmed again gets a new live row beside its withdrawn one (:238-245).

A task with more than one company writes no lesson, because the row has one company column, and withdraws as usual (:163-166).

The extraction has five callers. The single and the bulk disposition change and a completed retest run it inside their own transaction, so the verdict, the goal reopen and the lesson change commit together, and an extraction error rolls the verdict back (db/notification.go:512, :550, db/finding_retests.go:286). A terminal task status and POST /api/tasks/{id}/lessons/extract run it on its own (server/manager.go:1687-1689, server/lessons.go:104).

A finding's status has three writers in product code, all through SetFindingStatusTx: the operator's authenticated PATCH, a bulk route for several findings, and a completed retest whose verdict is fixed (db/notification.go:640-691, db/finding_retests.go:267-290). The retest verdict comes from the retester agent, in a session only a person can open. No planner or worker tool takes a finding status.

Deduplication needs identical text. Positive and negative actions embed the finding's free-text summary, so two tasks merge into one lesson only when their summaries match; cautions hold only the cue and verdict and merge widely. Text is cut by runes, 160 for the cue and 320 for the action, and a negative action cuts the summary so the status suffix survives (db/lessons.go:42-57, :285-288).

Operational cost

Lessons cost one query per task start and no model call. Extraction runs inside every disposition change whatever the lessons flag says. Digests cost one model call per folded block, with bodies reused when a block's member set and content version are unchanged.

8. Agent Integration

The lessons block is appended to the system prompt of the planner and the worker and to no other agent. frameLessonsBlock wraps it in the nonce-framed envelope with a fresh nonce per assembly and the marker stem rewritten inside the content (agent/data_envelope.go:59-68, agent/planner.go:577, agent/worker.go:584). Every other derived field goes in the user message inside the same frame: recent facts, findings, digests, related-task data, intent summaries, the assets an intent targets, and hints and credentials written by an agent (agent/data_envelope.go:72, :82-95, :107-230). The file's own comment prices it: the frame marks data and cannot stop a model from following it. The lessons block is the one framed field placed in the system prompt.

human_review is withheld. A person's disposition is what admits most lessons, and the agent that wrote the finding holds no tool that sets it. Two things keep the mark off. A model's retest verdict also admits lessons: fixed sets the finding's status and yields a positive lesson with a caution beside it. And what is reviewed is the finding. The lesson's own status is written by the extraction rule and by nobody else: no route or interface retires or adopts a lesson, and candidates are injected as they stand.

9. Reliability, Safety, and Trust

A triage verdict gates goal proof and undoes it

SetFindingStatusTx writes the status to the findings row and to the finding node's payload in one transaction (db/notification.go:661-674). Every finding read an agent has carries it: list_findings, the related-task overview, node_detail, and the list injected into each planner round (agent/tools.go:1084-1101, :1242, :618-623). An inheriting task reads the same node and sees the same label.

prove_goal refuses a finding whose status is false_positive, duplicate or ignored, and the round overview's findings_total leaves those three out (agent/tools.go:1453-1458, :1103-1125). A finding must also hold captured traffic whose host matches its asset, checked on the server (:1462-1470, db/finding_traffic.go:528).

Writing one of the three statuses reopens what the finding had closed. In the same transaction, each goal the finding's node proves goes from met to open, unless another proof of that goal would pass the gate: a finding whose status is not one of the three, or an observed fact that is neither target_response nor unverified (db/notification.go:590-625). The proves edge is kept. prove_goal and the reopen read one list of invalidating statuses (:566-583), and TestFindingStatusReopensProvedGoals covers the single, bulk and retest paths (db/goal_reopen_test.go:8).

These refusals are in the agent core and apply with lessons off.

Three limits:

  • risk_accepted proves a goal, by decision. The list's comment says it marks a real finding whose risk is accepted, and a test pins that it proves a goal and never reopens one (db/notification.go:563-565, agent/fact_provenance_test.go:282). The lesson rule files the same status as negative, Do not re-report without new mechanics.
  • The reopen changes the goal node only. The statement touches no task row. Whether a task that had finished on that goal runs again was not traced.
  • The node state does not move. A false-positive finding's node stays confirmed; dismissed exists in the schema and has no writer outside one test.

A fact declared as operator input is not checked

factProvenance returns operator_input for any fact whose declared source is operator_input, before it looks at the evidence or the intent (agent/tools.go:1738-1740). The source is a field of the tool call. A fact written with that source and confidence: observed therefore carries no activity tie, is not unverified, and passes every fact check in prove_goal (:1426-1451). The reopen query counts it as a remaining valid proof.

A committed case records exactly this from a worker's tool set, with no evidence line, and expects the provenance operator_input (agent/fact_provenance_test.go:129). Facts written before provenance existed carry no key and keep their declared labels (agent/tools.go:1429-1433).

The planner writes the rows its reads are scoped by

add_task_scope is in the planner's tool list, and AddAgentScope inserts what it is given once a named company exists (agent/tools.go:2591, db/task_scope.go:154-238). Neither scoped read asks who wrote a row. scopeTargetCTE joins every scope row of the task, so one call with kind=company brings that company's assets into list_assets (db/task_assets_context.go:79-88). The lesson scope lookup returns every company row (db/lessons.go:76-94), so the same call changes the lesson key:

  • on a task declared by domain, later lessons are stored under the added company, and that company's lessons are selected the next time the task's agents are built;
  • on a task with one company, a second company's lessons join the selection, and the task writes no further lesson.

What stands between target text and that call is a prompt rule: the untrusted data preamble tells the agent never to call add_task_scope because data asks (agent/untrusted_prompt.go:34). An agent's widening row is stored with expanded = true and returned to the caller with the flag (db/task_scope.go:225-233); no query filters on it.

Lessons of company-less tasks form one pool

A lesson's company is NULL when its source task had no company row, and a NULL row is selected for every task that has no company row, inside the category (db/lessons.go:125-130, :450). Tasks declared by domain alone are exactly those tasks, so two unrelated engagements declared that way read each other's lessons. A positive lesson's text is the finding summary, which names the source target's endpoints. docs/rsi-lessons.md:84 states the rule, the maintainer treats the pool as a product decision, and injection is off by default.

Two more routes lead into the pool:

  • Rows written before 17 November 2026. Until that day's change the scope lookup read tasks.company_id, which task creation does not fill, so every lesson was stored with no company. No migration rescopes them, and the dedupe key includes the company, so a new extraction writes a scoped twin beside the old row.
  • A deleted company or category. Both foreign keys are ON DELETE SET NULL (db/schema.sql:1555-1556). On the scratch database, deleting the second company raised the company-less task's selection from four lessons to seven.

What a withdrawal keeps

The withdrawal is an UPDATE that sets withdrawn_at on the live evidence row (db/lessons.go:339-349, :363-373). A retired lesson keeps its cue, action, status and the rows naming each finding and retest it rested on.

A restored support is a new row, so each withdrawal keeps its own timestamp. On a scratch PostgreSQL with the lifted DDL and statements, a finding confirmed, reversed, confirmed, reversed and confirmed again left three evidence rows, one live, and a second run of the last step added none.

The rows are not a mutation log. An evidence row has no creation time, so it says when a support was withdrawn and not when it was given, and the lesson's own status changes are an overwritten column with updated_at. audit_log rests on the coverage ledger alone.

Four edges, the first two re-derived on the scratch database:

  • A change inside the negative group replaces the lesson. false_positive followed by duplicate left the first lesson retired with its row withdrawn and the second candidate.
  • A retired lesson returns when another finding matches it. A second finding with the same cue and summary sets a retired lesson back to candidate, the withdrawn row beside the live one.
  • A reopened finding withdraws nothing. Moving a confirmed finding back to pending leaves its positive lesson selectable, by design and under test (db/lessons_test.go:881).
  • A deleted source cannot be withdrawn. No statement edits or deletes a lesson row. Deleting the source task or finding leaves the lesson with an evidence row naming an id that is gone, and extraction, which walks the task's existing findings, cannot reach it.

Because the extraction shares the verdict's transaction, a failure in it refuses the verdict: the status change, the goal reopen and the lesson change roll back together (db/lessons_test.go:1586). That holds with the lessons flag off.

The usage table rsi_lesson_usage records the rendered ids and has no reader outside one test.

Why three marks are withheld

human_review and bitemporal are covered above.

tombstone. Three near-misses. The negative lesson is a line of prompt text that the write path never consults: a re-reported finding lands as a new pending row. The duplicate check does consult stored findings on the write path, and a dismissed one can absorb a re-report, but the match is a model's judgement over every status alike, off by default, and lifted by the caller's own force_register. The retired lesson is keyed on a hash of its text, and the upsert does consult it, but a retired row with no live evidence is exactly the row it revives. The branch that keeps a retired row retired applies when live evidence remains, a state only hand-written SQL produces (db/lessons.go:316-326, db/lessons_test.go:790).

trust_state rests on three fields. The lesson status filters the selection. The finding's triage status filters goal proof and the overview count, reopens a goal it had closed, and is a label everywhere else. A fact's provenance is computed by the server at write time and never changes; unverified is refused as goal proof and filters no read. A fact's confidence and source are the agent's declaration, corrected downward by the provenance check, with operator_input as the exception above.

10. Tests, Evals, and Benchmarks

1,874 func Test in 430 test files. CI starts PostgreSQL 16 and runs go test -p 1 ./... with gofmt, go build and go vet, a race-detector pass over named packages, an advisory job on the newest Go release, and govulncheck (.github/workflows/ci.yml:9-129). I ran none of it.

The boundary tests are the strong part. TestExplorationDirectSourceReadView asserts that a source of a source is invisible, that a live source intent is absent from the frontier, the inherited list and finding lineage, and that an inherited fact cannot be mutated through the receiving store (db/exploration_sources_test.go:92). TestInheritedActivityReadsRequireTerminalIntent asserts five read paths do not return a reopened intent (:8). 11. For Your Own Build

Steal

Make cross-task inheritance explicit, one hop and live. A named relation, a cap, a query on every read so a deleted source disappears, and only finished work visible. Read-only falls out of scoping every graph write to the receiver.

Frame stored text when it re-enters a prompt. A per-message random nonce on both markers, and the marker stem neutralised inside the content.

Key a lesson's support on its sources, and withdraw without deleting. One evidence row per finding or retest lets a reversed verdict withdraw exactly its own support, a lesson shared by two findings survives the loss of one, and a retired lesson can say what it rested on.

Run the correction in the verdict's transaction. The status, the lesson withdrawal and the goal reopen commit together or not at all; the end-of-task pass is the fallback.

Undo what a claim closed when the claim falls. Keep the proof edge, check for another valid proof, and reopen the goal in the same statement.

Give a restored support a new row. A partial unique index over live rows keeps extraction idempotent and every withdrawal dated.

Tie a fact to recorded work on the server. Look for the evidence line in the activity log before trusting the labels the agent chose.

Rank a nullable scope match with IS NOT NULL AND =. A bare (col = $1) DESC sorts NULL first in PostgreSQL. Test the order with the unscoped row inserted last.

Parenthesise a compiled filter before appending the scope clause. Test it with a disjunction whose first branch matches a row on each side.

Log what was rendered, not what was selected. Have the renderer return the ids that fitted.

Stamp the writer on the server. A fact's origin is never taken from the tool's input.

Give a model's refusal to store a way back, in the refusal. The suppressed call returns the matched ids and the flag that overrides it, an id the model was not offered counts as no match, and every failure of the model stores.

Let summaries hide and never delete. A digest covers its members while they stay cold, a revived member reappears, and a re-compression starts from the source nodes.

Avoid

Do not give the reader a tool that writes its own scope. A filter over rows the agent can insert is a filter the agent sets.

Do not let NULL be a scope. A missing company, a deleted company and a row written before scoping existed all land in one pool that every company-less task reads.

Do not let the agent name its own exemption. A source label that skips the check is the label a confused agent will reach for.

Do not drop a suppressed write without a row. A duplicate verdict that leaves only a log line gives a person nothing to overturn, and matching against dismissed findings makes the loss likeliest where triage has already said no.

Do not let one status mean two things. risk_accepted proves a goal and writes a lesson that says not to report it.

Fit

The inheritance model and the scoped asset read suit any multi-task agent platform with one operator who trusts the planner with the scope. The lessons subsystem is rule built, evidence linked, company scoped, framed and off by default. It is safe to turn on where every task declares exactly one company, and not across tasks declared by domain alone.

12. Open Questions

  • Who retires or adopts a lesson by hand? RSI.md:53-55 calls status changes owner actions, the tests set both states with SQL, and no route does.
  • How will a multi-company task attribute a finding? docs/rsi-lessons.md:73-77 calls per-finding company attribution a later change.
  • Does a finished task run again when its goal reopens? The reopen writes the goal node and nothing else.
  • Who may declare operator_input? The worker and the operator's chat agent hold the same record_fact schema, and no check ties the label to an operator message.
  • Should a dismissed finding be a duplicate target? The pool is built without reading status, and the code does not say whether that is intended.
  • Is update_finding_report meant to cross tasks? Its write is keyed on the node id alone, and the duplicate check hands out ids from tasks the caller has no relation to.
  • Is expanded meant to gate a read? The flag is written and returned, and nothing consults it.
  • Is the outcome card's company meant to come from task_scope too? db/task_outcome.go:60 reads tasks.company_id, the column task creation does not fill.
  • Does restoring an archived task renumber its findings? If it does, a second extraction adds evidence for the same underlying finding. Not traced.
  • What does the agent SDK persist? Session compaction and transcripts live in a dependency this reading did not open.
