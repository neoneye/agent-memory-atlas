1. Executive Summary

Flair is a self-hosted identity and memory substrate for agents on Harper, whose memory reads all resolve one scoping rule written after a scattered copy of that rule leaked private memories. Private is the only value that withholds a row from another agent; everything else on an instance is open to every verified agent by design. The weak side is what sits under that rule: on a local install every verified agent runs as the Harper super user, so the resource-level checks are the whole boundary, and the memory feed bypassed them until 30 September 2026.

It describes itself as "[t]he identity and memory substrate for AI agents. Crypto-pinned. Federated. Self-hosted." — an Ed25519 keypair per agent, memory searched by meaning, and a "soul" of personality, values and procedures. The CLI installs and supervises Harper, writes a version-pinned stdio MCP adapter into each detected client, and ships thirteen packages beside it.

The read-scoping module exists because the rule was once scattered. Its header says so:

"Before this module existed, SemanticSearch had its OWN inline grant-resolution + a visibility === "office" global OR-clause that leaked ANY authenticated agent's read of ANY other agent's memories … Scattering the scoping rule per path is exactly how that leak happened — this module exists so it can't happen again: one rule, one place, every path imports it."

resolveReadScope returns one Harper condition and one in-process predicate with the same rule. Memory search and by-id get draw it through makeReadScope from a record-type registry, with a tripwire test that compares the composed resolver's mode and owner field against that registry. Semantic search, the session bootstrap, the memory feed, the attention query and the usage ledger call it directly (section 4).

The header's own list of paths is out of date. It names "the by-id GET guard in resources/auth-middleware.ts", which imports nothing from the module, and omits the feed, the attention query and the usage ledger. The by-id check is in the resource layer's makeByIdReadGate, and the middleware strips a non-admin's selection before it (resources/auth-middleware.ts:843-857). The comment is a claim about the code, and the call sites are the thing to read.

Two leaks around the rule were closed upstream, and both fixes test the path against the ordinary read. The memory feed subscribed to the raw table for any caller Harper admitted. A non-admin selection or property read was decided on the value the selection shaped, which carries neither owner nor visibility. Both are in section 9.

The migration invariant is argued, not asserted. The private exclusion is visibility != 'private', and the module explains why it is not visibility == 'shared': the second "would EXCLUDE them and silently retroactively privatize every legacy row". Choosing a predicate by what it does to rows written before the field existed is the habit worth taking from here.

The dedup gate never suppresses a write, with the bug that earned the capitals: an earlier client-side gate returned the existing record, and "the SECOND was silently dropped". The server computes a match signal, attaches it to the response, and writes anyway.

Two marks: scope_enforced on that resolver and negative_eval on an end-to-end search through the MCP tool that finds another agent's shared row and not its private one. trust_state, bitemporal, human_review, audit_log and tombstone are withheld, each for a reason in sections 5, 7 and 9.

2. Mental Model

A memory belongs to an agent and is open to the instance unless it says private.

Private is the only word that withholds a row from another agent. Archived, expired and superseded withhold it from default recall, for everyone including the owner.

A promotion must cite its reason to be shared.

A key proves who is calling, not what was said.

A memory is written live, with a durability class that sets its default visibility: permanent and persistent default to shared, standard and ephemeral to private, and an ephemeral row cannot be shared. It is edited in place unless the writer asks for a successor, which carries supersedes and closes the predecessor's validTo. It leaves default recall when archived, when its validTo or expiresAt passes, or when a successor names it. It leaves the store when its owner deletes it, when maintenance reaps an expired ephemeral row, or when an operator purges it.

Candidates are a separate table. Nightly distillation writes a claim as a pending MemoryCandidate; promotion turns it into a persistent memory, private unless a scope tag, a ruling and a rationale all survive re-verification.

Deployment and ergonomics

One npm install puts flair on the path; flair init --agent ID installs or reuses Harper, creates the keypair, checks semantic search and wires detected clients. Harper handles HTTP and persistence in one process over RocksDB. The README warns that a root-owned install makes semantic search "silently degrade to keyword-only", and that the install pulls roughly 130 MB of tooling Harper's SQL engine never uses, with a warning not to fix it with --omit=optional.

Who an agent is to Harper depends on how the instance was made. A verified non-admin agent runs as the flair-agent user when that user exists, and as the admin super user otherwise (resources/auth-middleware.ts:585-600). Only the Fabric branch of flair init creates it (src/commands/init.ts:390, :430), so a local instance runs every agent as the super user.

Feed. resources/MemoryFeed.ts:383 admits verified agents; :422-443 leaves admin and internal subscribers unfiltered and builds a non-admin subscription from an allowlist of options with the scope as rowFilter, then decides each event again in the loop.

Write. Memory.post and Memory.put redact credential-shaped text (resources/memory-redaction.ts), apply the durability-keyed visibility default, compute the dedup signal (resources/Memory.ts:334-352), and close a superseded predecessor after the successor is written (:939-943).

Promotion. resources/auto-promote-lib.ts:262-268 returns shared only when all three justifications are present; schemas/memory.graphql:358-364 states the rule.

Tests. test/integration/mcp-connector-principal-mapping.test.ts:256-283 and test/integration/feed-read-scope.test.ts carry the must-not-appear cases.

5. Memory Data Model

Content, owning agent, durability, visibility, embedding and usage, with promotionStatus, archived, supersedes, validFrom and validTo (schemas/memory.graphql:83-99), expiresAt, a server-stamped provenance blob and an opaque client metadata blob. A guard refuses an ephemeral row flipped to shared on POST and on PUT, and its end-to-end file labels a "POSITIVE CONTROL" and three "no over-fire" cases (test/integration/ephemeral-visibility-guard-e2e.test.ts:191, :204, :277).

bitemporal is withheld; the valid-time columns are there and the producers use the write clock. Retrieval honours an asOf against validFrom and validTo (resources/semantic-retrieval-core.ts:286-287), and a successor closes its predecessor's validTo at its own validFrom. Memory.post defaults validFrom to createdAt (resources/Memory.ts:1661-1662), and the agent-facing writers set createdAt to now: flair memory add (src/commands/memory.ts:128) and the MCP and client successor paths, which delete validFrom from the copied row (resources/mcp-tools.ts:550-556). Only the bridge importer carries a foreign validFrom (src/bridges/runtime/import-runner.ts:148). The record side is weaker still: createdAt may be backdated by the caller, and updatedAt is overwritten by every update and by the close patch.

trust_state is withheld, and every candidate field was checked. visibility filters, and it is writer intent resolved by the same predicate that earns scope_enforced. provenanceStatus on the trust block is epistemic and deliberately decides nothing: resources/trust-block.ts:18-20 says it "INFORMS THE READER ONLY" and "MUST NEVER enter an authority / scope / attribution / dedup decision anywhere", enforced by test/unit/trust-block-zero-authority-tripwire.test.ts. promotionStatus on a memory has no read filter anywhere in resources/. archived filters default recall, and the module that sets it calls it "a VISIBILITY flag, not a deletion" — a retire switch the owner flips, with no claim about truth (resources/MemoryArchive.ts:9-14). Superseded is derived from another row's pointer rather than stored.

6. Retrieval Mechanics

Hybrid semantic and lexical, fused by rank, with a BM25 index beside the HNSW vector index. The default scoring is raw, after a measured finding — recorded in the comment beside it — that a composite durability and recency multiplier outranked better matches. Archived rows, rows whose validTo or expiresAt has passed, and predecessors named by a co-present successor are dropped unless the caller asks for them (resources/semantic-retrieval-core.ts:235, :295). A temporal word in the query only nudges recency; an incidental "today" once emptied the result set when it filtered.

The README says the displayed percentage is a similarity with a keyword boost, that hybrid ranking means the top result need not have the highest percentage, and that it "is not a probability that the memory answers your question correctly".

7. Write Mechanics

Write, then signal. The dedup gate compares the write against the single top cosine candidate of the same agent — "never cross-agent" — and requires both a cosine threshold and a Jaccard token overlap, with no fallback to the second candidate. It rarely claims a duplicate and never acts on the claim (resources/Memory.ts:334-352).

Credential-shaped text in content, summary and trigger is redacted on every agent write and on the feed ingest, and the write response reports the stored text (resources/memory-redaction.ts:1-27). Federated content is left alone.

human_review is withheld. POST /PromoteMemoryCandidate admits any non-anonymous caller, lets an agent promote its own candidate, and defaults reviewerId to the caller; the only reviewer check refuses the reserved machine namespace (resources/PromoteMemoryCandidate.ts:17-36, src/rem/promote-policy.ts:230-235). The agent that owns a candidate can approve it. tombstone is withheld. A rejected candidate is a status on a record, and nothing consults a rejected value when the next distillation writes a claim.

8. Agent Integration

flair init --agent ID writes a keypair and wires every detected MCP client to npx -y @tpsdev-ai/flair-mcp@VERSION, pinned to the CLI's own version. The built-in /mcp endpoint is OAuth-guarded and off by default: an unset FLAIR_MCP_OAUTH leaves it unregistered, and only the literal true turns on both the route and the OAuth component. The README separates the two paths as two trust situations, a local client and a remote connector.

9. Reliability, Safety, and Trust

Within an instance the boundary between agents is the word private. Per-owner grants remain an inspectable relationship and gate no read; private is "the ONLY owner-only exception"; the federation push filter keeps private rows on the instance (src/commands/federation.ts:204-207). For a personal instance that is the intended knowledge-refinement model. For a shared one, a careless agent registration reads everything not marked private.

On a local install, Harper's own role checks do not separate agents. Every verified non-admin agent resolves to the admin super user when flair-agent does not exist (section 3). Any resource left on Harper's default allowRead, which admits the super user, is then open to every agent. Every class in resources/ that extends Resource and defines a read method also defines allowRead, and every exported table has a resource class that does.

The feed was the resource that relied on that default. Until 87bd59c5… on 30 September 2026, FeedMemories defined no allowRead and its connect subscribed to the raw table. On a local instance a verified agent therefore received every memory event, private rows included. The fix's test runs each case both before and after flair-agent is provisioned, and compares the feed with the by-id read.

A shaped by-id read was decided on the shaped value. Until 04e091c1… on 27 September 2026, makeByIdReadGate passed the caller's target to Harper and checked what came back. Harper reads /Memory/ID.content as a property selector, so the gate saw a string with no owner and no visibility, which the predicate admits. The middleware's own check looked up the raw path segment, ID.content, which names no row. Read from the code; nothing was run.

Supersession exists and editing defaults to overwrite. memory_update overwrites in place unless preserveHistory is set, in which case the successor carries supersedes and the predecessor's validTo is closed. The close runs after the successor is written, so a failure leaves two live rows rather than a lost one (resources/Memory.ts:939-943).

audit_log is withheld. MemoryDeletionHistory records a deletion only for permanent and persistent rows, records no update, and the purge path removes its own rows (resources/memory-deletion-history.ts:25-26, :54, resources/MemoryPurge.ts:157). The doctor audit-log check probes Harper's engine audit log, which is the database's, not a named record of memory mutations.

The key proves the caller. Memories are not encrypted with it, and losing it "costs the identity, not the data". The federation receiver verifies a per-record signature when a record carries one and merges an unsigned record by default (resources/Federation.ts:136-155); no code in the tree produces that signature, and the sync batch is signed as a whole. attribution on a usage row is "OPAQUE — never parsed, never fed to an LLM, never rendered", to be trusted as "nothing more than a label" (schemas/memory.graphql:226-229).

11. For Your Own Build

Steal

Put the scoping rule in one module and make every read path import it, then add the test that trips when a second copy appears.

Choose the predicate by what it does to old rows. != private and == shared differ only on records written before the field existed, and one of them privatises your history silently.

Decide a by-id read on the stored row, never on what the caller's selection shaped. A projection without the owner field is a record your predicate has not seen.

Test a secondary path against the primary one. A feed test that asks "does the feed deliver exactly what the by-id read returns" catches the next bypass; restating the rule does not.

Never let a de-duplication gate drop a write. Compute the signal, return it, and store the record.

Avoid

A comment listing the call sites of a single-source module. The list here names a guard that moved and misses three paths that arrived later; the importers are the list.

A privilege fallback that elevates. Falling back to the super user when the least-privilege user is missing makes every resource relying on the database's default authorization open to every agent, which is how the feed leaked.

Fit

For one person or one trusted team on one instance, the open-within-org model is coherent and the scope code is carefully kept. For agents that must not read each other, it does not fit without marking everything private. Provision flair-agent by hand on a local instance before relying on Harper's roles at all.

12. Open Questions

Whether flair-agent is meant to be absent on local installs. The fallback comment calls such instances "pre-migration", and no local code path creates the user.

Whether federation verification covers content. The receiver checks a record signature when present, and nothing in the tree produces one.

What the soul costs at read time. It is central to the pitch and sits outside the memory paths read here.
