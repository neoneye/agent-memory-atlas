1. Executive Summary

GitMem is an MCP server that gives a coding agent a store of scars (mistakes), wins, patterns and anti-patterns, and makes the agent answer for them: a scar is refused at write time unless it carries at least two counter-arguments, and a PreToolUse hook blocks a consequential command while recalled scars have no accepted confirmation. The weak points are where those two rules meet the store: the gate counts confirmations rather than matching them to scars, the counter-argument rule counts strings without reading them, and every scar read path draws from one cross-project index.

At write time, a scar must argue against itself.

function validateScar(params: CreateLearningParams): string[] {
  const errors: string[] = [];
  if (!params.severity) {
    errors.push("Scars require severity (critical, high, medium, low)");
  }
  if (!params.counter_arguments || params.counter_arguments.length < 2) {
    errors.push("Scars require at least 2 counter_arguments");
  }
  return errors;
}

The counter-arguments are stored in a TEXT[] column, folded into the embedding text on the Supabase path, and returned on every search result shape, so the objection travels with the claim to the point of use. The rule is a count: the Zod schema bounds each string at 2,000 characters and sets no minimum, so two empty strings satisfy it.

At read time, every recalled scar must be answered, once. confirm_scars implements what its docstring calls the refute-or-obey protocol — APPLYING with past-tense evidence, N_A with a scenario comparison, REFUTED with a risk acknowledgment. It refuses the whole batch if any recalled scar is left unanswered, if any evidence is under 50 characters, or if the last recall never reached the store. hooks/scripts/recall-check.sh turns that into a hard block on git push, npm publish, deploys and writes to .sql or .env files. The hook's condition is "recalled scars exist and the confirmation count is zero", so a second recall after an accepted confirmation surfaces scars that the gate does not hold (section 9).

The loop closes in ranking. At session close every recalled scar becomes a gitmem_scar_usage row — explicit, acknowledged, refuted, or none for one surfaced and ignored. The next session_start runs a SQL function that sets each scar's decay_multiplier from its 90-day dismiss rate, and local recall multiplies similarity by it.

2. Mental Model

A memory is a learning: a typed, structured lesson with a title, description, severity, counter_arguments, applies_when, why_this_matters, an action_protocol and self_check_criteria. The agent treats it as something it must answer, and the answer, more than the learning, is what the system tracks closely.

A learning has two lifecycle values and one grade that moves:

  • active (is_active true or absent) — in the index and in every read.
  • archived (is_active = false) — set by archive_learning, which the agent holds; excluded from the index load, the SQL search function, the free-tier BM25 path and log. The tool takes a reason, echoes it in its reply, and stores nothing of it (src/tools/archive-learning.ts:162-165, :211-222).
  • decay_multiplier — a float from 0.1 to 1.0, rewritten by refresh_scar_behavioral_scores() as 1 − 0.8 × dismiss rate for a scar surfaced at least three times in 90 days, where none and refuted count as dismissals (schema/setup.sql:383-422). A refuted scar sinks; it does not leave.

Nothing deletes a learning, and nothing moves one into a state that says it was wrong. A learning written in error is archived with a reason that is discarded, or left to decay as agents refute it.

Two further stores carry memory across sessions with their own lifecycles. Threads are open work items with a six-value status (emerging, active, cooling, dormant, archived, resolved), deduplicated by embedding against the caller's own session's open threads. Thread suggestions are proposals from session-embedding clusters, pending until promote_suggestion or dismiss_suggestion — both registered tools the agent holds.

3. Architecture

A TypeScript MCP server on stdio (gitmem-mcp on npm) with thirty canonical tools and short aliases. src/ holds tools (the MCP surface), schemas (Zod input schemas), services, hooks, commands and diagnostics. A Claude Code plugin under hooks/ registers shell hooks on SessionStart, UserPromptSubmit, PreToolUse, PostToolUse and Stop.

Storage has two tiers. Pro is Supabase: Postgres with pgvector from schema/setup.sql, reached over PostgREST only, with embeddings from OpenAI, OpenRouter or a local Ollama. At start the server loads the 500 most recently updated active learnings with their embeddings into one in-process index, persists them to an on-disk cache keyed by store, and on later starts fetches only rows whose updated_at moved. Free is JSON files under .gitmem/ (~/.gitmem unless GITMEM_DIR is set), searched by BM25 over title, keywords and description.

Deployment and ergonomics

  • Free tier: nothing runs but the server; no API key; the store is plain JSON a person can read and repair.
  • Pro tier: a Supabase project with setup.sql applied and an embedding provider. Without a provider embed() returns null and semantic search returns nothing.
  • Install: npx gitmem-mcp init detects the editor and writes MCP config, hooks and a rules file; hook installation merges per event and keeps foreign hooks.
  • The hooks need only bash and node; jq is used when present.

5. Memory Data Model

gitmem_learnings (schema/setup.sql:11-39):

  • learning_type CHECK IN ('scar','win','pattern','anti_pattern'); severity CHECK IN ('critical','high','medium','low'); scar_type, default operational, where process, incident and context set temporal decay in the SQL search function
  • counter_arguments TEXT[], applies_when TEXT[], problem_context, solution_approach, why_this_matters, action_protocol, self_check_criteria
  • is_active, decay_multiplier, repeat_mistake, related_scar_id, repeat_mistake_details JSONB
  • project, source_date, persona_name, embedding vector(1536), created_at, updated_at

source_date is the write date (create-learning.ts:116); nothing records when a lesson became true separately from when it was written.

repeat_mistake has a reader and no writer. services/analytics.ts:233 selects learnings with repeat_mistake: "eq.true" and reports each against its related_scar_id with the reason from repeat_mistake_details. Across the tree the only other references are the schema and migrate-local.ts, which copies the column between stores. A learning created through this package carries the column default, false, so the report section that lists scars which failed to prevent a recurrence is empty unless something outside the package sets the flag.

gitmem_scar_usage (schema/setup.sql:132-147) is the half that is written:

reference_type TEXT CHECK (reference_type IN
  ('explicit', 'implicit', 'acknowledged', 'refuted', 'none')),
surfaced_at TIMESTAMPTZ, acknowledged_at TIMESTAMPTZ,
referenced BOOLEAN, execution_successful BOOLEAN, variant_id UUID

session_close writes one row per recalled scar. APPLYING maps to explicit, N_A to acknowledged, REFUTED to refuted, and a scar with no confirmation and no closing-reflection match to none.

execution_successful is the agent's account of compliance: true when the end-of-session reflect_scars outcome is OBEYED, or when the confirmation was APPLYING or N_A; unset for REFUTED; false for an unaddressed scar. It does not observe whether the guarded action succeeded.

variant_id links a usage to an A/B wording of the scar, assigned in services/variant-assignment.ts and gated by hasVariants() to the dev tier.

gitmem_threads (setup.sql:165-185) carries project, a status CHECK over six values, vitality_score and an embedding. The local cache threads.json is typed ThreadObject, which has no project field; the project's own comment says "one flat file holds every project's threads" (src/services/thread-drift.ts:15-17).

6. Retrieval Mechanics

Four read paths reach scars: recall (the one the gate watches), search, prepare_context, and the UserPromptSubmit hook's quick retrieve. On the Pro tier all four call localScarSearch(query, k, project) when the index is warm. Its third parameter is declared _project and the body is getLocalVectorSearch().search(query, k) over a singleton keyed "__all__" (local-vector-search.ts:325-342, :374-381). The file states the design: "Unified cache — all scars loaded into single instance regardless of project. At ~400 scars, semantic similarity handles relevance better than project partitioning."

The index holds at most 500 learnings across every project. INDEX_ROW_LIMIT = 500 (startup.ts:108) caps the bulk load, the delta manifest and the health check's remote count alike, ordered by updated_at. A store past that size serves recall from its 500 most recently touched active learnings, and the health comparison cannot see the rest.

Ranking is cosine similarity × decay_multiplier (:236-240). recall then drops results under 0.45 on Pro and under 0.4 on the free tier's normalised BM25 scores. search over-fetches matchCount * 3 when a severity or type post-filter is set. counter_arguments come back in every result shape (search.ts:151, :269, :301).

The cold-index fallback. While the index is not ready, recall calls a PostgREST RPC. setup.sql defines gitmem_scar_search (:322-376), which filters is_active, applies scar_type temporal decay and the multiplier, and takes no project argument. scarSearchCandidates() tries it first for the default table prefix and match_<table>_weighted second, falls through only on PGRST202, and remembers the first that answers (supabase-client.ts:641-711). Between 8 August and 22 September 2026 the fallback called only match_gitmem_learnings_weighted, which no file in the tree defines. The fix's commit message records that every cold recall on a store built from setup.sql returned PGRST202 and nothing.

Where a project predicate sits. Session history at session_start filters { agent, project } (session-start.ts:196); the decision panel filters by project in memory (:354); log filters by project on both tiers (log.ts:125, :219-222). Threads in Postgres go through one query builder that always sets project and excludes inactive statuses (thread-scope.ts:128-156), with isInScope as its in-memory mirror. The predicate is absent on every scar read, and on the free-tier threads.json, which has no project to filter by. Free-tier search merges storage.query("decisions", {}) — every project's decisions — into its results (search.ts:157-165).

7. Write Mechanics

create_learning validates, embeds, inserts, writes knowledge-graph triples, and on the dev tier generates scar variants. A scar failing validation returns success: false with stored_in: null and the errors, and writes nothing. After the insert it awaits an index refresh and reports index_refreshed: false if the reload failed; the learning is saved either way.

Every write tool reports durable and stored_in, and a zero-row PATCH counts as not durable (src/services/write-result.ts, archive-learning.ts:166-179).

session_close is the heavy write: closing reflection, decisions, threads, scar usage, transcript capture where the store has the tables, and relevance data on the recall's metrics row. Columns the store lacks are probed and skipped rather than sent (src/services/store-columns.ts).

The free tier writes whole JSON files. Past 10 MB a collection keeps its most recent 80% and drops the rest, and a file that fails to parse is read as empty, so the next write replaces it (local-file-storage.ts:36-66).

Operational cost

  • create_learning is synchronous: one embedding call, one insert, and an awaited index refresh that fetches only changed rows.
  • recall on a warm index is in-process: one query embedding and a linear scan of at most 500 vectors.
  • session_start fires the decay refresh and the index warm-up without waiting. The decay function touches only rows whose multiplier changes, so it does not invalidate every client's disk cache.

8. Agent Integration

The agent is expected to call session_start, recall before consequential work, confirm_scars, create_learning when something goes wrong or right, and session_close at the end. The hooks make three of those hard to skip:

  • SessionStart tells the agent to call session_start, which shows the last session, open threads and recent decisions for the project.
  • UserPromptSubmit classifies the prompt and injects matching scars.
  • PreToolUse runs credential-guard.sh on Bash and Read and recall-check.sh on Bash, Write and Edit; the second also nags after ten tool calls without a recall, at most every 90 seconds.
  • Stop blocks ending a meaningful session that has not run session_close.

The agent's tool surface includes every verb that changes memory state: create_learning, archive_learning, confirm_scars, reflect_scars, record_scar_usage, promote_suggestion, dismiss_suggestion, resolve_thread and cleanup_threads.

9. Reliability, Safety, and Trust

The gate counts; it does not match. recall-check.sh:93-99 reads the number of recall-sourced scars and the number of confirmations from session.json, and :147 blocks only when the first is positive and the second is zero. confirm_scars persists confirmations only when every recalled scar is answered, so the first block is per-item. After that the confirmation count stays above zero for the session, and scars from a later recall reach a consequential command unblocked. The server's enforcement.ts:116-131 does match by id through hasUnconfirmedScars() (session-state.ts:520-528), and it returns a warning, not a refusal.

A failed recall cannot be confirmed past. When no recall-sourced scars exist and the last recall recorded a failure, confirm_scars returns valid: false with "Cannot confirm — institutional memory was not reached" (confirm-scars.ts:196-220). An empty result and an unreachable store are different answers, and the protocol tells them apart.

Scope enforced — withheld. The predicate is real on threads in Postgres, on session history and on the session-start decision panel, with isolation tests on the thread builder. Every scar read path carries none, by design: recall, search, prepare_context, the prompt hook, and the RPC fallback, whose comment says project_filter is left out to match the cross-project index. The free-tier thread cache cannot carry one. The mark needs the stored key applied on the read path of the memory the system is about, and here that path is the one deliberately left unscoped.

Trust state — withheld. The one axis that filters learnings is is_active, a lifecycle flag set by archiving, whose reason is discarded, so the stored state cannot say whether a learning was wrong, obsolete or a duplicate. severity and decay_multiplier rank. Thread status filters threads and describes work, not belief.

Human review — withheld. promote_suggestion and dismiss_suggestion are registered at src/tools/definitions.ts:740 and :760 and dispatched at src/server.ts:264 and :269; confirm_scars is at definitions.ts:53 and server.ts:169. The agent that sees a pending suggestion can promote it, and the agent shown a scar can confirm it and proceed.

Audit log — withheld. gitmem_scar_usage records what was surfaced and what the agent said about it, which is retrieval feedback. Learnings are updated in place by the archive PATCH and the decay UPDATE, and no table records those mutations as events.

Tombstone and bi-temporal — withheld. An archived scar's text, resubmitted, is a new active row; thread dedup consults open threads only. source_date and the triples' event_time are both the write clock.

Negative eval — earned, on the free-tier list path. Section 10 has the case.

The dismissal counter cannot reach its own threshold. dismiss_suggestion's header says "Suggestions dismissed 3+ times are permanently suppressed", and getPendingSuggestions filters s.status === "pending" && s.dismissed_count < 3. dismissSuggestionById sets status = "dismissed" and increments the count. The matcher that decides whether a recurring topic matches an existing suggestion opens with if (suggestion.status !== "pending") continue; (thread-suggestions.ts:93). The recurrence creates a fresh suggestion with dismissed_count: 0, and no writer returns a dismissed suggestion to pending. So dismissed_count never exceeds 1, the < 3 guard is unreachable, and dismissal suppresses a record rather than a topic.

Archive failed on customer stores until 20 September 2026. The PATCH sent archived_at, which setup.sql does not create, and PostgREST rejects a write naming an unknown column, so on a store provisioned from setup.sql no learning was archived. Commit 1ec20a35… probes for the column first.

Free-tier durability. Section 7's eviction and parse-failure behaviour means the free tier can lose learnings without an error the agent sees.

11. For Your Own Build

Steal

  • Require counter-arguments before you accept a lesson, and return them with it. Two, minimum, enforced at write time, folded into the embedding and carried in every result. Then set a minimum length, which this one does not.
  • Make consultation per item. Every surfaced item answered with an applies, does-not-apply or override verdict, each with its own evidence rule, and refuse the batch if any is missing.
  • Refuse to confirm after a failed retrieval. "Nothing matched" and "the store was not reached" must produce different answers, or the gate certifies an outage.
  • Block on consequential actions only. A PreToolUse hook matched to a short list of irreversible commands is the right blast radius.
  • Record none as a usage outcome, and feed it back. A scar shown and ignored lowers its own rank; a refuted one sinks without being deleted.
  • Separate surfaced_at from acknowledged_at so the ignore rate is measurable.
  • Give a lesson an action_protocol and self_check_criteria.

Avoid

  • Do not gate on a count when the rule is per item. Store the set of confirmed ids and block on the difference, or the second batch walks through.
  • Do not let a comment name the deployed schema. The fallback here was renamed to match one operator's store on the strength of a survey, and the test was written to the rename. Assert RPC names against the schema file the project ships.
  • Do not skip non-pending records in a dedup matcher when the non-pending state is what you are enforcing, and do not key a suppression on a generated id.
  • Do not ship a column whose only consumer is a report. repeat_mistake has an analytics reader and no writer.
  • Do not accept an archive reason you will not store.

Fit

For a team that wants an agent held to its lessons rather than merely shown them, on a store of a few hundred scars shared across repositories on purpose. The design assumes one team's lessons generalise across projects, and it breaks down in two directions: a multi-client operator who needs one client's scars kept from another's, and a store large enough that 500 recent rows stop being the useful ones. The free tier is a different product — BM25 over JSON with no embedding and silent eviction — and suits a single developer trying the protocol.

12. Open Questions

  • Who sets repeat_mistake? Nothing in the tree; whether the operator's own store has a writer outside this package is not visible here.
  • Does the decay loop help? refuted and none lower a scar's rank; no committed analysis compares recurrence for decayed and undecayed scars.
  • What happens past 500 learnings? The cap is fixed and the health output does not disclose it; whether any deployment has reached it is not recorded.
