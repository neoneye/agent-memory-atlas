1. Executive Summary

MemContinuum is a decision store for Claude Code projects in which a ruling, once committed, cannot be edited: the store's own pre-commit hook diffs every recorded link against the last commit and refuses any change outside three forward-only lifecycle fields. The authority stamped on a ruling then decides what it may do — only the owner's own or ratified words can fail a drift check or ride in every session's opening digest. The weak side is that the store delivers decisions and enforces nothing about their use: a declined option is shown to the model and never checked against, and the authority is whatever the writer typed.

The README states the problem as two failures at once: decisions that scroll out of context and get re-litigated, and an agent working file-locally that writes a helper which exists two directories away.

The unit is a question, and the answer is a chain nothing can rewrite. One markdown file per topic; its body is an ordered list of links, newest first; each link is one ruling with its own date, status, kind, authority, evidence and rationale. A change of mind is a new link carrying reverses and a reason_for_change, and the link it reverses keeps its text.

memlint.py --against-ref REF enforces that (memlint.py:2269-2347, :2877-3197). It compares every link against the same link at a git ref and reports any changed field outside {link, status, superseded_by, promoted_by}. That is a set difference, so a field added to the schema later is frozen without anyone listing it. A link whose parsed fields survive but whose raw bytes changed is refused as a reformat. So is a removed link, a deleted record file, a new link inserted below a recorded one, and recorded links reordered. Three lifecycle fields may each move forward once, only into a terminal state, and only as the sole change on that link.

The same check covers the topic's standing: list, which decides what every session opens with (:2743-2874). A commit that adds or removes a standing link must add exactly one standing_marks: row for that change, carrying who recorded it, when, on whose authority, from what source and why. Recorded rows are frozen by fields and bytes like links, a row matching no change is refused, and the row's authority must be owner-level.

The store's pre-commit hook runs the schema lint and then that check, and exits 1 on either (hooks/pre-commit-append-only.sh:173-179, :192, :201, wired by scripts/repo-init.sh:1717). git commit --no-verify skips it. The post-commit hook then re-runs both checks against the parent commit and leaves a marker the next session start reports (hooks/post-commit-reindex.sh:258-374). The marker is removed by the next clean commit, which compares only against its own parent. The installer's documentation says the real guarantee for a shared store is the same check in CI behind a protected branch (hooks/install-hooks.md:321-324); no workflow, template or script in the tree provides that job. Each link and each standing mark carries recorded_by and recorded_at, so the chain is the store and the record of every ruling made in it, which earns audit_log.

Authority decides what a record may do. Five values are allowed on a ruling, and they collapse into three citation tiers: owner-verbatim and owner-ratified are CONSTRAINT; the other three are HOLD when they carry evidence and CONTEXT when they do not; anything not active is CONTEXT whatever its authority (memidx.py:5831-5850). Search defaults to active, so a superseded, declined or provisional link row is not returned unless asked for (:3613-3640, :3689-3693). The session-start digest carries a standing link only when it is active and owner-level (:6669-6672). A discrete status that withholds a memory, applied as a filter, is what trust_state asks for.

One more mark. negative_eval: one search over three records planted with the same term returns the real topic and asserts both inbox drops are absent, then flips a single flag and asserts both are present (tests/test_memidx.py:3418-3482).

human_review is withheld. Anything under inbox/ indexes as type: inbox whatever its frontmatter claims and stays out of search; a provisional link is never checked by drift; the linter refuses a status edit back toward active. What is absent is an actor the producing agent cannot be. The route out of staging is appending a link whose authority is owner-verbatim or owner-ratified, and the linter describes the second as "the orchestrator's own paraphrase" (memlint.py:141). The agent writes the link with its own Edit and Write tools; the linter checks the shape and never that an owner affirmed it. A standing mark's owner-level authority is the same kind of field: the caller passes it to mark-standing --authority, and recorded_by falls back from --recorded-by to MEMCONTINUUM_RECORDED_BY to memidx (memidx.py:12562-12571).

Projects are separated by storage, not by a filter. Each repository is wired on its own, with its own store, hooks and project name, and one database is refused outright for a second project (memidx.py:1075-1080). Several repositories run side by side and none reads another's rulings; the cost is that no two projects can share memory. Two findings sit against the design. A declined ruling is delivered, not enforced: the pre-edit chain hands every link to the model regardless of status, and nothing keys on the rejected value. Every hook but the commit gate fails open: a missing index, a missing interpreter or a slow lookup means the edit proceeds, and a file changed from the shell gets no lookup at all.

2. Mental Model

A memory is a question with a history of answers, and the history is the point. Asking "what do we do about hidden files in the processed count" returns not the current answer but the chain that produced it: what was adopted, what was declined and because of what, what reversed what and on which of three stated grounds — new evidence, changed context, changed mind.

Belief is graded by who said it, per field. The same link can hold a ruling the owner spoke verbatim and a rationale that is an agent's reading of why, and the schema keeps them apart on purpose. There is no paraphrase value, and owner-ratified exists so an inference can be promoted without being confused with the owner's own words.

A memory is used at the moment of an edit, not when someone remembers to ask. When the model issues an Edit or Write, a PreToolUse hook resolves the path to the topics whose code_refs cover it and returns their chains as additional context. The hook runs before the edit reaches disk, and its context reaches the model with that edit's result: it governs the next move, not the edit that triggered it (hooks/pre-edit-chain.sh:6-14). When nothing binds the file, it searches on the path's words and labels the result "No recorded decision binds this file. Nearest by search -- may be unrelated" (hooks/mc-fallback-lib.sh:28). The lookup is bounded at two seconds, and a timeout says the absence of a matching decision was not established. A bound file or symbol whose bytes differ from the hash captured at binding is named beside the chain as changed since capture.

A few rulings apply everywhere. A topic may list some of its own links as standing, and every session opens with a capped digest of those that are active and owner-level, at most 24 links and 4,800 bytes (memidx.py:5744-5745). Which links are standing is itself audited: every change to the list leaves a frozen, attributed row.

Nothing forgets. There is no decay, no consolidation and no summariser; a ruling stops applying by being superseded, declined or marked historical, and its text stays where it was written.

3. Architecture

Two Python programs and a shell layer around Claude Code.

  • memidx.py (13,414 lines) — the indexer and every read command: reindex, search, chain, for-path, why, drift, standing, context-pack, unmapped, check, code-search, code-census, stats. Four commands edit topic frontmatter or the inbox and commit nothing: bind, mark-standing, anchor-backfill and propose-bindings --write-inbox. It owns the SQLite schema for both databases, the FTS5 tables, the embedding pipeline and its background worker, the anchor hashing, and the three enforcement classes.
  • memlint.py (3,541 lines) — validation in three parts: a schema and consistency pass over the tree, a citation check of cited commits and file:line references against --code-root, and --against-ref, the append-only check that compares links, anchor rows, standing marks, link order and current against a git ref.
  • mc_text.py (124 lines) — the content-term vocabulary shared by the indexer and the prompt-query channel.
  • chunkers/ (2,566 lines) — a Python AST chunker, a Swift chunker and a tree-sitter backend with pinned grammars for JavaScript, TypeScript, Java, PHP, Rust and Lua.
  • hooks/ (9,056 lines of shell) — pre-edit-chain.sh is the retrieval hook, mc-fallback-lib.sh and mc-query-lib.sh its search fallback, ledger-post-edit.sh the edit ledger, pre-commit-append-only.sh the store's git gate, post-commit-reindex.sh the reindex, sessionstart-remind.sh the standing digest and session nudge, userprompt-remind.sh and newfile-nudge.sh the write-side nudges and the prompt search, code-refresh.sh the code-index refresh, mc-store-lint.sh the two commit checks shared by the pre-commit and post-commit hooks, mc-watchdog.sh the deadline wrapper.
  • scripts/ (7,110 lines of shell) — repo-init.sh installs and wires everything; memcontinuum-update.sh re-renders drifted installs; the -decide, -state and registry scripts manage a per-machine registry of which repositories have a store.
  • bench/ — a synthetic corpus, a query set, three runners and a scorer (section 10).

The store itself is a git repository of markdown. The index is a projection and is disposable; the pinned tree-sitter grammars are an explicit exception to the project's own >= policy, because an unpinned grammar upgrade would change chunk shapes without moving the index fingerprint.

Deployment and ergonomics

  • What has to run: Python with PyYAML for everything, plus fastembed and numpy only for the vector and hybrid modes, imported lazily so for-path, chain and check stay dependency-light. SQLite is embedded. CI and the installer install from requirements.lock, which pins exact versions with hashes; requirements.txt and pyproject.toml carry minimums.
  • Fully local and offline: yes, including embeddings.
  • Hand-repairable: the store is markdown in git, and the index rebuilds from it.
  • Install: memcontinuum-setup.sh and scripts/repo-init.sh, which wire the Claude Code hooks, the two store-side git hooks and a registry row.

4. Essential Implementation Paths

  • Freeze a recorded link. _link_diff_errors (memlint.py:2274-2347) takes one link as it was at a ref and as it is now, subtracts {link, status, superseded_by, promoted_by} from the union of both field sets, and reports every remaining field whose value moved. status may go from active or provisional to superseded, historical or declined and no further; superseded_by may be added only in that move; promoted_by may be added once. A lifecycle move bundled with any body edit produces an error for each.
  • Freeze its bytes and its place. _link_raw_spans (:2416) locates each link's exact text span by indentation, and check_append_only refuses a link whose parsed fields are identical and whose bytes are not, treating a span it cannot extract as changed (:3166-3197). A new id following a recorded one is refused as out of order (:3138-3153), and recorded ids must keep their relative order (_link_order_errors, :2814), because the chain head is the first active link in file order. A removed link (:3160-3165) and a deleted or renamed record (:2973-2989) are errors.
  • Pair a standing change with its row. _standing_pairing_errors (:2794-2811) requires one new standing_marks: row per id added to or removed from standing: and refuses a row that matches no change. _standing_marks_freeze_errors (:2743-2791) freezes recorded rows by fields and bytes and requires new rows above old ones. _standing_marks_errors (:242-283) refuses a row whose authority is not owner-level. _current_discipline_errors (:2848-2862) refuses a current: that moves while the newest active link has not.
  • Freeze a code baseline. An anchors: row records the SHA-256 of the file or the one chunk a code_refs entry named when it was bound, with the capture kind, date, code commit and worktree state. _anchor_freeze_errors (:2681-2714) freezes recorded rows; _anchor_errors (:172-220) requires each row's ref to be present in code_refs and its link in links.
  • Judge new links more strictly than old ones. _new_link_errors (:130-155) refuses an unknown kind and an owner-verbatim ruling phrased as a question. Under --against-ref these are errors only for links absent at the ref; a plain lint reports them on recorded links as warnings, since frozen history cannot be repaired in place.
  • Gate the commit. hooks/pre-commit-append-only.sh runs the schema lint, then memlint.py --against-ref HEAD --staged ROOT, and exits 1 on an error from either (:173-179, :192, :201). An unset root, a different repository, an unborn HEAD, a missing interpreter or an unrecognised linter result each exit 0 with a logged reason. hooks/post-commit-reindex.sh re-runs both checks with HEAD~1 as the ref and writes a <project>.relint-failed marker under MEMCONTINUUM_HOME on a finding (:258-374); sessionstart-remind.sh prints one line while it exists (:448), and the next clean post-commit run removes it (:320).
  • Classify a ruling. invariant_enforcement_class (memidx.py:5831-5850) returns context for any non-active status, then constraint, hold or context by authority and evidence. "Evidence" here means a list holding at least one non-blank string (:5805-5817); the citation check is a separate lint pass and does not feed the class. memlint.py:1471-1497 computes the same tiers from raw YAML and imports memidx's two authority sets.
  • Run the drift gate. cmd_drift (memidx.py:5960-6040) checks each link's invariant against current source, sends a provisional link to revalidate unchecked, names skipped ones, and returns 1 on a constraint violation or, under --strict-holds, a hold violation. A person runs it; the store README template lists the command (templates/store-README.md.tmpl:45).
  • Resolve a path to decisions. cmd_for_path (:5214) opens the index read-only and exits 5 on an index that needs migrating, which the hook logs as index-needs-migration. topic_matches_for_path (:4217) keeps the project's topics with a code_refs entry matching the file by prefix, glob or path#symbol; topic_chain_lines (:4974-4992) then selects every link for that topic by topic_path, ordered by sequence, with no status filter, and places any anchor note after the header.
  • Fall back on a miss. pre-edit-chain.sh:816 and newfile-nudge.sh:741 run search --decisions-only --read-only --hydrate on the path's words. --decisions-only restricts hits to topics, links, incidents and investigations (memidx.py:3676-3687); --hydrate renders each hit's chain under a byte cap that keeps the current link first (:3879-3904, :5004).
  • Deliver the standing digest. standing_entries (:6639) reads each topic's standing list and keeps a link only when it is active and owner-level; cmd_standing (:6679) refuses rather than truncates over the cap, and sessionstart-remind.sh delivers it.
  • Pack decisions for a brief. cmd_context_pack (:7110) prints the standing digest, the chains bound to the named files, any --topic chains and a labelled FTS guess for --query, under a hard byte cap that drops whole topics and names them, ending in a SHA-256 of exactly the bytes printed. It opens the index read-only. The hash is printed, not stored.
  • Stage a proposal. infer_type (:734-745) returns inbox for anything whose first path segment is inbox, overriding the file's own type:; cmd_search excludes those records and their link rows unless include_inbox is set (:3734-3742).
  • Notice a shell edit. hooks/ledger-post-edit.sh diffs the tree with git status after a Bash or unrecognised tool call and appends {path, kind, content_sha256, seen_at, root, source} rows to the session's ledger, which is what the nudges read.

5. Memory Data Model

A topic is a file with frontmatter — type, id, title, area, project, current, code_refs, standing, standing_marks, anchors, tags — and a body of links. current is hand-set to the newest active link and the linter errors, naming the correct value, when it disagrees.

A standing mark is one row per change to standing: — link, action (add or remove), date, recorded_at, recorded_by, authority, source, why. The rows are never indexed or delivered; they exist to be audited.

An anchor is one row per bound code_refs entry and link — the entry, the link, a SHA-256 of the file or of one chunk, the capture kind (ruling, bind or backfill), the capture date, the code commit and the worktree state. A prefix or glob reference never carries one. One baseline exists per entry and link; a new baseline needs a new link.

A link carries link, date, status, kind, an optional reverses with a reason_for_change drawn from three values, a ruling and a rationale each with text and authority, alternatives as a list of {option, rejected_because, authority}, evidence, revisit_if, an optional invariant, typed edges, assumptions, recorded_by and recorded_at.

A concept (type: concept) is the Anatomy layer: what the code already contains, with implemented_by, tested_by, an owner boundary and governed_by topics.

Temporal: date on the ruling and recorded_at on the recording are both record times, and validity is positional — a ruling applies until a later link supersedes it. There is no interval and no as-of query. bitemporal withheld.

Trust: five authorities and five statuses, read on the search default, the standing digest and the drift gate. trust_state earned.

Audit: the link chain and the standing marks, frozen against the last commit, with standing, current and link order judged against them. The rest of the frontmatter is outside the guard. code_refs, which decides which files a ruling governs, changes with no event beyond git history. Adding one through bind leaves an anchor row; adding one by hand, or as a prefix or glob, leaves nothing. type is unguarded too, and a change of type takes a topic out of the standing digest (docs/SCHEMA.md:386-388). Nothing in the tree removes a binding. The plain lint requires an anchor row's ref to be in code_refs, and the guard freezes the row, so an anchored reference cannot be removed by a commit that runs the hook.

Scoping: a project column that one database can only ever hold one value of, because each repository has a store of its own. Withheld — see section 9.

Tombstone: a declined status and per-link rejected alternatives, frozen once written and delivered on the write path, keyed on the topic rather than on the value and enforcing nothing. Withheld — see section 9.

6. Retrieval Mechanics

Five surfaces, and the important one is not a query.

for-path is the automatic surface: a file path in, every topic whose code_refs cover it out, each with its whole chain. Matching is by path prefix, fnmatch glob or path#symbol, and only the last takes part in marker verification. Concepts matching the path come too, and each brings the topics that govern it. A bound file or symbol is hashed against its anchor row, and the chain carries one of a fixed set of labels — changed since capture, never captured, missing, not checked — that never alter the link's status or authority. The lookup also runs for a worktree checked out beside the repository, and declines without a search an edit under the parent folder that belongs to no wired project.

The search fallback runs when for-path finds nothing for the file being edited or created. It searches on the path's words with the default status filter, restricted to decision records, takes at most two hits and labels them as a guess. Each hit carries its chain, capped at 2,000 bytes by default.

The standing digest opens every session and every compaction with the standing links of all topics — citation lines only, ordered and capped, and refused rather than truncated over the cap. With a code root configured, one line after it names standing links whose bound code changed since capture; that line is the first thing dropped when the cap bites.

The context pack is the same material handed to someone outside the session. context-pack FILE... prints the standing digest and the chains bound to the files a reviewer or a dispatched agent will touch, each link with its authority and store path, ending in a SHA-256 of the exact bytes. The rendered rules file tells briefs to open with it (templates/memcontinuum-rules.md:27); nothing runs it automatically.

search is FTS5 by default, with vector and hybrid modes behind a lazily imported fastembed. Its defaults lean the same way as the mark: status defaults to active, and inbox records are excluded. In hybrid mode, when the FTS top hit shares no vocabulary with the query, the ranking steps aside to the vector result and reports fusion: vector-only. The embedding fingerprint covers the model name, dimension, pipeline version, prefix, normalisation and fastembed's installed version.

An opt-in prompt channel, switched on per project by an environment variable or a projects file, derives search terms from the user's prompt, never from agent reports or task notifications, and makes at most one guess per prompt (hooks/userprompt-remind.sh:364-372).

why is the reviewer's direction — from a file or symbol to the concept to the topics that govern it — and it prints declined links on purpose, because the question it answers is why the code is strange.

Failure modes. Every path but the commit gate fails open. A missing or uninitialised index returns a named reply and no decision; an index that needs a schema migration gets a one-line refusal from the pre-edit lookup, which never writes it; a stale index answers from what it has. The two-second timeout and the labelled fallback are the two places where the model is told what was not established. A file edited through Bash gets no lookup; the ledger records it afterwards from git status over each code root and its linked worktrees, which does not show a file committed in the same call or one under an ignored path.

7. Write Mechanics

Nothing extracts. There is no summariser, no consolidation pass and no background writer; a memory exists because a person or an agent wrote a link and committed it. No production code writes a link. Three commands write topic frontmatter, each by line insertion that must round-trip through the parser, printing the diff and committing nothing (memidx.py:12219-12229): bind adds a code_refs entry and its anchor row, mark-standing changes standing: and prepends its row, and anchor-backfill gives an older reference a baseline labelled backfill. propose-bindings reads a session's edit ledger and fallback searches and prints suggested bindings, optionally to inbox/proposals/. The nudges are the only push: one fires when files have been edited under no decision topic, the other when the conversation has moved on shortly after real edits.

Correction is an append. The predecessor keeps its text and gains a terminal status; the successor names it in reverses and states which of three grounds applies. The linter refuses a kind: reversed link whose target is active, and refuses reverses without a reason_for_change.

Citations are checked when a code root is bound. With --code-root, the linter resolves a cited commit, subject or file:line against that tree; an unresolvable one warns, and --strict-citations makes it an error. The commit gate does not pass a code root.

Concurrency is git's. The store is a repository, the index is a projection, and the post-commit hook rebuilds it.

Operational cost

  • A pre-edit lookup is one SQLite open and two queries; a miss adds one search, measured in the hook's own notes at under a second in hybrid mode. Both sit under the two-second watchdog.
  • A commit pays the schema lint and the --against-ref pass over the staged records.
  • A reindex is proportional to the store; embeddings are optional and filled by a background worker, with a first model download of about 133 MB.
  • An anchor check hashes each bound file or chunk under the hook's budget, and a check the budget cut short is labelled unchecked rather than reported.
  • No model call anywhere in the memory path.

8. Agent Integration

The model never calls a recall tool. The hooks put the standing digest in front of it at session start, the governing chain or a labelled guess with the result of an Edit or a Write, and nudges when edits have accumulated under no topic. The hook sees the edit's final content and only adds context; nothing in the tree denies an edit. Two skills — memcontinuum and memory-search — give it the deliberate surfaces. The person's surfaces are the CLI, the markdown store itself, and inbox/.

The install decision is itself recorded per repository in a registry keyed by the origin remote when there is one and the working tree path otherwise, so a repository that declined is never asked again. That declined is a different vocabulary from a link's declined status, and a reader grepping the tree will meet both.

9. Reliability, Safety, and Trust

Trust state — awarded. Five authorities, five statuses, three enforcement classes. The status excludes rows on three reads: the search default, which the hook fallbacks and the memory-search skill use; the standing digest; and the drift gate, where provisional withholds a link from enforcement entirely. The classification exists twice, over YAML and over SQLite rows, with the authority sets shared so the two cannot diverge. The anchor labels sit beside the status and do not join it: a ruling whose bound code changed since capture is still active and still a constraint. The limit is the producer: authority and status are fields in a file the writing agent edits, and nothing verifies that an owner-verbatim ruling came from the owner.

Audit log — awarded. The chain is the record of the rulings made in it: each link names when it was ruled, who recorded it, when, what it reverses and on what grounds. The standing marks extend it to the one frontmatter field that puts a ruling in every session: each addition to or removal from standing: is a dated, attributed row with a source and a reason, and the guard refuses the change without its row. The append-only property is enforced by a linter whose frozen set is a subtraction rather than a list, by a byte comparison that catches a regenerated file, by an order check on links and rows, and by the store's own pre-commit hook.

Four limits. The hook is a local git hook that --no-verify skips; the post-commit re-run names such a commit at the next session start, on that machine, until the next clean commit removes the marker, and the CI re-run the documentation recommends is not shipped. A commit whose previous version of a record could not be parsed is treated as a repair, and the documentation states that a removed link, anchor block or marks block passes it with a note (docs/SCHEMA.md:389-396). code_refs and type change with no row. And a mark's authority and recorded_by are what the caller passed, the same limit trust_state carries.

Human review — withheld. Inbox records are typed as such regardless of what they claim and excluded from search; provisional links are never enforced; no edit can move a status toward active. Promotion is an appended link at owner authority, written with the same Edit and Write tools the agent holds, and the linter checks its shape rather than who wrote it. No surface in the tree checks an actor; the recorded search for isatty and approve finds three comments.

Negative evaluation — awarded. The inbox exclusion is asserted against a populated result set with the flag as the only variable, and re-asserted in the other direction. The FTS mode it uses needs no embedding model, so the positive control runs with PyYAML alone. The standing-marks, binding and context-pack suites assert refusals and cap behaviour, not what a read must withhold, so the mark rests on the inbox cases alone.

Scope — withheld, and the withholding is not a finding about isolation. Project isolation is enforced by construction: one decision database belongs to one project, records is keyed by path alone, and open_db refuses to open a store under a second --project rather than letting the two mix — "opening the SAME physical file for a different --project would silently evict/overwrite that project's rows" (memidx.py:1046-1051). project=? appears 67 times in memidx.py, 11 of them in updates and deletes; the chain read keys on the topic path alone. The separation starts above the database: repo-init.sh is a per-repository initializer (scripts/repo-init.sh:2-7) that wires the hooks into that repository's own settings.local.json (:1204-1206) and renders store-side wrappers exporting its store root and project name (:389-390). The default store sits beside the checkout and is named for it (scripts/mc-registry-lib.sh:773); where it is placed under $HOME instead, on a Windows-mounted checkout, a name already belonging to a different checkout or project is disambiguated or refused (:756-764). Nothing here leaks between projects, and the same construction means no two projects can share a store.

What the mark asks for is narrower than isolation: a stored scope key that partitions co-resident memory on the read path. A store that holds exactly one scope cannot demonstrate that, because the predicate has nothing to exclude — the same line drawn for Agentic Context Engine, where one skillbook belongs to one agent. The code index is the multi-project store, keyed (path, project, code_root), and what it holds is chunks derived from source rather than anything that could turn out to be false.

Tombstone — withheld, and it is the closest miss here. The schema is well equipped for one: a declined status meaning considered and not adopted, a declined kind, and per-link alternatives each carrying the option, the reason it was rejected and its own authority — all frozen once committed. The rejection is delivered on the write path: topic_chain_lines selects every link for a topic with no status filter, so the model about to edit a governed file receives what was declined along with what was adopted. Two things keep the mark. It is keyed on the topic and reached by file path, not keyed on the value, so the same rejected idea under another topic or in another file meets nothing. And the delivery is text a hook hands to a model and cannot refuse: re-adopting is a legitimate move the schema models with kind: restored.

Bitemporal — withheld. date and recorded_at are both record times and validity is positional in the chain.

What the fail-open discipline costs. Every hook except the commit gate is written never to block an edit, which is a defensible choice for a tool that sits in front of someone else's work. The pre-edit hook could refuse: it runs on PreToolUse with the edit's final content in hand. The repository ships a probe that drives a real session against a denying stand-in hook, and its docstring describes denial as established, with no result file committed (bench/pretooluse_rewrite_deny_probe.py:10-13, :52-54). The real hook returns context only. The guarantee is about the store — a recorded link cannot be rewritten through a commit that runs the hook — and not about the work: nothing ensures a decision was consulted, only that it was offered when the index was present and the path went through a tool the hooks see.

10. Tests, Evals, and Benchmarks

2,704 test functions in 23 modules and 57,754 lines. test_memidx.py and test_memlint.py carry the schema, the enforcement classes, the append-only diff and the inbox exclusion; test_standing_marks.py (109 functions) the pairing, freeze, order and current rules, including a refused agent-authority row; test_binding.py (132) the anchor rows, their capture, their labels and their cap order; test_context_pack.py (30) the pack's cap, omissions, hash and blind mode; test_memlint_citations.py the citation check; test_hooks.py and test_write_hooks.py the shell layer, including the search fallback and the standing digest; test_repo_init.py and test_update.py the installer and updater; test_stats.py the log parser. There are golden files, a macOS smoke test and a bash-3.2 runner. CI runs the suite on Python 3.12 and 3.13 from the locked requirements. None of it was run for this reading.

bench/ is a public retrieval benchmark. A synthetic 32-record corpus about a fictional sync product, 69 queries — 20 by file path, 49 by question, sliced into paraphrase, exact-term and plain — and three runners: no memory, a TF-IDF keyword baseline, and MemContinuum in FTS, vector and hybrid modes. The scorer reports Recall@1, @3, @10 and MRR per slice. A negative control reruns each runner against a kind-preserving shuffle of query and expected answer, and fails a runner whose gain does not clear one standard error.

The README's own limitations section is specific: the corpus is clean by construction and its numbers are upper bounds; the answer key is one agent's judgment; the control catches a stateless, deterministic runner that ignores the query and is beaten by a counter or a random sampler, both kept as test fixtures. No score file is committed, and a private gate over real incident history depends on fixtures the repository does not publish.

The hook log carries a topics= field so that a matched edit becomes a gradeable sample, and stats reports pre_edit_topics_named, topics_distinct and top_topics. No analysis of that log is committed.

11. For Your Own Build

Steal

  • Enforce append-only with a diff against a ref, not with a convention. Comparing each record against itself at the last commit turns "we never edit history" into something a commit can fail.
  • Freeze by subtraction, and freeze the bytes. Naming the four fields that may move and freezing everything else protects a field added next year; a byte comparison catches the YAML dumper that rewrites every record while changing no value.
  • Make a lifecycle move the only change on a record. A status flip bundled with a text edit is how an append-only store quietly stops being one.
  • Pair a membership change with a frozen row. Requiring exactly one attributed row per id added to or removed from a list, and refusing rows that match no change, audits a mutable pointer without making the pointer itself append-only.
  • Hash what a decision was bound to. A baseline captured at binding lets a later delivery say the code moved since, labelled by how the baseline was captured, without pretending the ruling is now wrong.
  • Tighten rules for new records only. A stricter check that errors on new links and warns on frozen ones lets a schema improve without demanding edits the append-only rule forbids.
  • Grade authority per field, not per record. A ruling can be the owner's words while the rationale beside it is an agent's guess.
  • Say what retrieval failed to establish. A timeout that reports the absence of a decision was not established, and a miss that labels its nearest guess may be unrelated, keep a model from reading silence or a guess as a ruling.
  • Retrieve on the tool call, not on the model's discretion. A hook that resolves the file being edited to the decisions that govern it needs no cooperation from the model.
  • Publish a negative control with the benchmark. A shuffle that a query-blind runner cannot beat, and a written list of the runners that do beat it, is a benchmark that can say it measured nothing.

Avoid

  • A scope column in a store that can hold only one scope. The predicate reads like a partition and is a stamping guard; write down which it is.
  • Recording what was declined and never checking against it. The reasons are captured, immutable and delivered, and nothing consults them as a precondition — the mechanism is one lookup short of a real tombstone.
  • An authority label the writer chooses. A tier that decides what blocks work is only as strong as whoever can type owner-verbatim.
  • A guarantee that lives in a local hook. A check --no-verify skips needs a server-side twin, and the twin has to ship, not be recommended. A post-commit re-check that clears at the next clean commit makes a bypass visible once, on one machine.
  • A context hook that could refuse and only informs. The edit's content is in the hook's hands before it is applied; the declined values are in the index.

Fit

Right for a small team or a solo developer running agent-driven work, in one repository or several, who wants the reasons to survive the session and the reasoning to be citable afterwards. Each repository is wired and stored on its own, so several run side by side without leaking into each other. The append-only discipline is the strongest part and the part that costs least to adopt. Wrong if you need memory shared across projects, which that separation rules out by construction, memory about people rather than about code, a check that a proposal contradicts a declined ruling, or any guarantee that a decision was actually read.

12. Open Questions

  • Will a declined ruling ever be checked rather than shown? The reasons are recorded and immutable, and the Edit and Write hook already holds the edit's content before it is applied. An edit made through the shell gets no lookup at all, so a check there needs a different entry point.
  • Can one store serve several projects? The refusal is honest about why it cannot — records keyed by path alone — and the code index shows the shape that would fix it.
  • What do the benchmark numbers look like on real decisions? The private gate exists for that and its fixtures are unpublished.
  • Should code_refs get the standing list's treatment? It decides which files a ruling governs, a hand-added or glob reference leaves no row, and an anchored one cannot be removed at all.
  • Should a change of type be guarded? It is the remaining way to take a topic out of the standing digest without a row.
