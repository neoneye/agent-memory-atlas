On this page

1. Executive Summary

OpenYantra is a local, single-user memory toolkit that keeps a structured model of one person as sheets in a LibreOffice workbook, written through one gated writer and served to Claude Desktop and Cursor over MCP. The gate is the notable part: an injection scan that can hold a write for a person to release, an admission filter, vocabulary checks, and a row on an append-only ledger sheet.

A sheet change and its ledger row land in one atomic save, under a file lock that every process takes. The lock is also the defect. A write that validation rejects or the conflict guard refuses logs its refusal through a path that takes the same lock again on a second file handle. On Linux and macOS that waits forever, and the writing process blocks. The MCP memory tools and the dashboard write a separate JSON store with a secret filter and an injection block and no ledger. Nidra promotes a matched phrase to Beliefs once, and marks a belief superseded when a revert names it; only one context list honours the mark. The SQLite engine has no producer.

LICENSE is the MIT text; SPEC_LICENSE dedicates the protocol's table schemas, sheet templates and interchange formats to the public domain under CC0 1.0.

The README describes a SQLite WAL store shared by the HUD, the CLI and the MCP server. At this commit the HUD and the MCP sheet tools share the workbook, the MCP memory tools use a JSON file, and SQLite holds only hand-drawn graph edges. Three marks are earned, all on the sheet engine: audit_log on the ledger sheet, human_review on the quarantine, and negative_eval on a resolved loop and a Done task the session context must leave out. Section 9 gives the reason for each of the four withheld.

2. Mental Model

A memory is a row in a sheet of chitrapat.ods. The sheets are Identity, Goals, Projects, People, Preferences, Beliefs, Tasks, Open Loops, Session Log, Agent Config, the ledger (Agrasandhanī), Inbox and Corrections, plus Quarantine and Security Log created on first use. A row is identified by its first column — the attribute, task text or loop topic — and carries Confidence (High, Medium, Low, Inferred), Source (User-stated, Agent-observed, Agent-inferred, System), Importance 1 to 10 and Last Updated (openyantra/core.py:75-103, :2734-2830).

A row becomes a belief by passing four gates in order, and nothing marks it as less than true afterwards:

  • Raksha redacts secrets, then scans the joined field text. A confirmed injection, jailbreak, impersonation or zero-width pattern sends the write to Quarantine; a suspicious one adds a _security_flag column and lets it through (core.py:707-725, openyantra/yantra_security.py:457-555).
  • Admission drops a write whose content contains a noise phrase, whose content is at most two words including a filler word, or whose importance is below 2, with no ledger row (core.py:116-168).
  • Validation rejects an unknown sheet or a value outside the controlled vocabulary (core.py:409-424).
  • Conflict refuses an update that would change a High-confidence field from a request that is not High (core.py:426-444).

A row stops counting through a lifecycle column read by the context builder: a loop resolved, a task Done, a project not Active, a goal not Active or In Progress (core.py:1154-1168). Identity, People and Preferences rows have no such column and change only by overwrite. Beliefs carry Superseded_By, which Nidra fills when a revert names a belief, and only the session context's beliefs list reads it (section 9). The delete operation is in the vocabulary and has no branch in the committer, so nothing is ever deleted (core.py:84, :450-569). A git revert adds a new Session Log row labelled Reverted / Superseded Decision; the reverted commit's own row is untouched (openyantra/yantra_git.py:106-127).

The cognitive store is a second memory with no relation to the first: a JSON list of notes with a key, a type, an agent name, content, tags and a timestamp. A write replaces the note with the same key case-insensitively, and a delete removes it (openyantra/cognitive_db.py:40-135). Only the MCP memory_* tools and the dashboard's cognitive routes reach it, and no context builder reads it.

Control is hybrid. The agent writes through MCP, a person writes through the HUD, the dashboard, the CLI, Telegram, LibreOffice or Obsidian, and Nidra resolves loops when someone runs it.

3. Architecture

Everything is one Python package, openyantra/, constructed per process. Each of the MCP server, the dashboard, the Telegram bot, the iOS Shortcut server, the mail daemon, the CLI and the git hook opens its own OpenYantra on the same workbook.

  • core.py holds OpenYantra, the writer LedgerAgent and the queue WriteQueue. The constructor replays the queue, opens the search index, and creates a SQLite SyncEngine beside the workbook (core.py:639-677).
  • yantra_security.py is Raksha: regex lists, secret redaction and trust tiers keyed on the writer's agent name.
  • vidyakosha.py is the search sidecar: a FAISS flat inner-product index, a pickled BM25 index and a JSON registry of indexed rows.
  • yantra_sqlite.py creates fifteen tables mirroring the sheets, plus _meta, _sync_state and edges, at every start (yantra_sqlite.py:128-381). Only edges is written in product code, by the dashboard.
  • cognitive_db.py and cognitive_mcp.py are the JSON store and a hand-written line-delimited JSON-RPC server announcing protocol 2024-11-05.
  • yantra_ui.py is a FastAPI app on 127.0.0.1:7331 serving UI/v4/dashboard.html and UI/v4/hud.html; desktop.py opens either in pywebview or a browser.

Beside the workbook the package keeps sanchitta.json, chitrapat.db, cognitive_memories.json, settings.json, vidyakosha.faiss, vidyakosha_bm25.pkl, vidyakosha_registry.json, a pratibimba/ folder of per-agent snapshots and yearly chitrapat_sessions_<year>.ods archives.

A write is a whole-file rewrite. The writer parses every sheet with pandas, writes them all to chitrapat.tmp.ods and moves it over the workbook with os.replace (core.py:453-569, :571-594). _workbook_lock takes an exclusive portalocker lock on .chitrapat.ods.lock around the whole of _process and around _write_sheet (:332-352), and the queue file takes one on sanchitta.lock around each load and save (:242-262). portalocker>=2.7 is a core dependency in pyproject.toml, install.sh and install.ps1, and the Dockerfile installs the package with pip install -e .. Both run unlocked, silently, when the import fails or the lock call raises (:67-71).

Deployment and ergonomics

The core needs Python 3.9 or later with odfpy and pandas. Search adds scikit-learn and faiss-cpu, MiniLM is optional, and the dashboard adds FastAPI, uvicorn and webauthn. No API key is needed to store anything. Nidra calls a local Ollama on localhost:11434 when one answers and falls back to a template sentence. Everything runs offline.

The store is the point of the design. A person can open chitrapat.ods in LibreOffice, read every sheet and fix a row by hand. Such an edit bypasses Raksha and the ledger. The yantra sync command that the skill file describes as importing such edits calls SyncEngine.import_ods, whose body opens the file and returns a note: "stub returns OK for now" (yantra_sqlite.py:762). A hand edit takes effect because the workbook is the store; the search index sees it at the next write.

The first-run path is curl … install.sh | bash or install.ps1; section 8 lists what each writes.

4. Essential Implementation Paths

  • Sheet write. OpenYantra.request_write (core.py:701-753) runs Raksha, then LedgerAgent.submit, which appends the request to sanchitta.json, calls _process, and removes the entry by request id in a finally block (:315-321, :280-286, :368-407). _process first returns already_committed for a request id the ledger sheet holds (:354-366), then runs admission, _validate, _check_conflict and _seal, and _commit_and_audit writes the sheet change and the written ledger row in one save; a rejection or conflict goes to _log_audit. On written, request_write calls VidyaKosha.sync over the whole workbook, because the incremental_update it checks for is not defined (:736-740). It then asks SHEET_TABLE_MAP for an edge table; that map is keyed Tasks, OpenLoops, while sheet names carry emoji, so the lookup is always None (:747, yantra_sqlite.py:61-77).
  • Replay. OpenYantra.__init__ calls replay_queue, which empties the queue and runs _process on every request in it (core.py:643-648, :323-326).
  • Capture. MCP sheet tools (cognitive_mcp.py:401-460); the dashboard and HUD through POST /api/inbox (yantra_ui.py:193-198, UI/v4/hud.html:408); yantra inbox (cli.py:274-277); Telegram commands and plain messages (telegram_bot.py:151-240); the iOS Shortcut server (ios_shortcut.py:55-93); the SMTP daemon (yantra_mail.py:20-49); Obsidian import (yantra_vault.py:181-245); the post-commit hook (yantra_git.py:63-127); and the CrewAI, LangChain and OpenClaw adapters.
  • Routing. route_inbox sends each unrouted Inbox row to the sheet a keyword list picks, as a Low-confidence Agent-inferred row, then marks the Inbox row by its full content (core.py:786-822, :2423-2444).
  • Consolidation. NidraConsolidator.consolidate clusters the last 25 sessions, resolves loops, promotes preferences and logs a summary session (yantra_nidra.py:245-385), from yantra dream, POST /api/nidra/consolidate or the HUD.
  • Context. load_session_context (core.py:1145-1192) feeds build_system_prompt_block (:1194-1240) and build_context_markdown (:1866-2025), which MCP get_system_context returns; SutraCompiler.compile packs a token budget (yantra_sutra.py:71-365).
  • Search. OpenYantra.search (core.py:1249-1306) over VidyaKosha.query (vidyakosha.py:355-439), reached through the LangChain retriever and the CrewAI adapter; CognitiveMemoryStore.search (cognitive_db.py:137-181); SyncEngine.traverse (yantra_sqlite.py:923-967).
  • Correction. Update, resolve and supersede through _commit_and_audit, the last from Nidra's revert pass (yantra_nidra.py:288-324); the corrections queue (core.py:824-864, yantra_ui.py:205-221); quarantine release (core.py:1458-1478, yantra_ui.py:238-241); cognitive delete (cognitive_db.py:123-135); session-log archival (core.py:1325-1370).

5. Memory Data Model

The controlled vocabularies are sets in core.py:75-84: project, task and goal statuses, four priorities, Yes/No, three preference strengths, four confidence values, four sentiments, four sources and seven operations. Column names follow the template, and _commit_and_audit adds any new field as a new column, so a writer that names a field wrongly widens the sheet instead of failing.

Row identity is the first column's text. update, resolve, archive and supersede build a mask on the first column equal to row_identifier and change every matching row (core.py:487-536). An update that matches nothing appends a new row with the requested fields, so a mistyped task name sent to the dashboard's complete route creates a row with status Done and no task text.

Provenance is caller-supplied. Source and Added By come from the request. add_task, add_project and update_identity hardcode source="User-stated" and confidence="High", so a task the agent creates through MCP is recorded as the person's statement (core.py:1018-1058).

Scope. One workbook per person. The one key is the Agent Config sheet's Agent column, which load_session_context uses to pick the instructions an agent receives, with ALL as the wildcard (core.py:1148-1152). The cognitive notes carry an agent name that no read consults.

Time. Last Updated in UTC seconds, Opened on loops, Deadline on tasks and goals, and the ledger's request timestamp. There is no validity time. TTL_Days on loops is read by check_anishtha_ttl, which reports expired loops and changes nothing (core.py:898-927).

Belief columns. Beliefs carries Contradiction_Flag, written as No by Nidra's promotion and as Superseded by <successor> by a supersede, beside Superseded_By (core.py:521-536, :2783-2784). diff_beliefs returns same-topic groups to the CLI and the dashboard's insights (core.py:866-896, :2121, :2169-2176).

The SQLite schema mirrors the sheets with lowercase columns and a UNIQUE request id on ledger for idempotent writes (yantra_sqlite.py:128-381). SyncEngine.write has callers only in tests/test_setu.py.

Committed data files. The root chitrapat.ods is a workbook bootstrapped on 20 May 2026 at v2.12, holding a first name, a city and an occupation in Identity. Its Session Log has the bootstrap row twice, 15 seconds apart. Its ledger has the same four writes twice, under the same request ids and timestamps: the queue replay as it ran before e6a19a1, when nothing removed a processed entry, recorded in the project's own file. cognitive_memories.json is an empty list, and settings.json holds the defaults with empty key fields. .gitignore lists all three as user data. openyantra/chitrapat_template.ods is the blank template.

6. Retrieval Mechanics

Context injection is assembled from sheets, not search. load_session_context returns the identity map, the agent's instructions, Active projects, unresolved loops sorted by importance and capped at 15, Active or In Progress goals, tasks whose status is not Done, pending corrections, the unrouted Inbox count and the Beliefs rows with no Superseded_By (core.py:1145-1192). Archived and Blocked tasks pass that filter. No other code reads the beliefs list. build_context_markdown caps each section at four to eight items and adds Values and Constraints beliefs at High confidence, the first five People rows and Strong preferences (core.py:1866-2025). It is the only reader that uses Confidence to exclude a row. Two other compilers read Beliefs from the sheet with no superseded filter: yantra context takes the first five of importance 7 or more (yantra_context.py:147-157), and SutraCompiler filters projects, loops, goals and tasks by status and Beliefs by nothing (yantra_sutra.py:226-240).

Semantic search indexes eight sheets: Identity, Goals, Projects, People, Preferences, Beliefs, Tasks and Open Loops (vidyakosha.py:237-240). Each row becomes [sheet] column: value … without the confidence, source and date columns. The vector arm is FAISS IndexFlatIP over TF-IDF with truncated SVD, or MiniLM when installed; BM25 runs at k1 1.5 and b 0.75. Each arm is normalised by its maximum and fused at 0.7 vector to 0.3 BM25, and OpenYantra.search then multiplies by importance and a one-year recency ramp (vidyakosha.py:355-439, core.py:1249-1306). No status filter applies, so a resolved loop, a Done task and a Cancelled project rank like live ones.

A per-agent snapshot freezes the registry at session start and keeps querying the live FAISS and BM25 indexes, so positions in a rebuilt index can address a different row of the frozen registry (vidyakosha.py:441-455, :492-502).

The HUD's recall fetches the Beliefs sheet and filters it by substring in the browser (UI/v4/hud.html:433-445). MCP memory_search is a substring match over key and content with type, all-tags and date-prefix filters, and returns every match. graph_traverse is a recursive CTE walking edges both ways for up to six hops, with a path-substring cycle guard.

The MCP server injects nothing on its own; the model has to call get_system_context. Cognitive notes are never part of any context.

7. Write Mechanics

Every write is an explicit call. No model extracts or rewrites memory; Nidra's Ollama call produces only the summary sentence it logs as a session.

Admission drops short filler. _is_worth_remembering joins the content fields, leaving out importance, confidence, priority, status, source, author, date and deadline. It drops the write when that text contains one of six phrases such as user said thanks, or when it is at most two words and one of them is a filler word such as sure, noted or great (core.py:116-168). "Make sure the backup runs" is admitted; "Sure thing" is dropped with status filtered and no ledger row. The filler set lists thank you and got it as entries, and a single word never equals either. Session Log, Inbox and Corrections writes skip the filter.

Conflict detection is a refusal with nowhere to go. A conflicting update returns resolution: pending_user; the requested value is kept only as text in the ledger row's reason (core.py:386-396). Most MCP and adapter writes are High confidence, so the guard rarely fires.

Duplicates are made, not removed.

  • When the workbook lock is not taken, a second process replaying the queue while the first is inside _process applies the request again; an add lands a second row (section 9).
  • Obsidian import reads every line of Inbox.md again on each sync and never clears the file (yantra_vault.py:232-245).

Nidra. prune_and_resolve_loops resolves an open loop when its topic, or its first three words of four or more letters, appears in the decisions and topics of the last 30 sessions (yantra_nidra.py:191-243). Revert rows are part of that corpus. detect_promotable_preferences scans the last 30 sessions and 20 Inbox rows for phrases such as user prefers, always use and never prefer (yantra_nidra.py:104-189). Each new match longer than eight characters becomes a Beliefs row with Topic Pref: <first 35 characters>, Position User Preference: <phrase>, Confidence High, Source Agent-inferred and Importance 8, written through request_write as NidraConsolidator with the topic as its row identifier (:173-182, :255-286). The phrase is the text after the trigger, so never use tabs for indentation and always use tabs for indentation both become User Preference: tabs for indentation. Three checks sit in front of it:

  • Already stored. The known set holds each stored Position, the same Position without its User Preference: prefix, and each Topic, and a phrase promoted in this run joins it (:111-120, :183-186). A second run adds nothing, and a superseded row keeps its phrase out.
  • Reverted. A pre-pass over the last 50 sessions strips the Reverted / Superseded Decision [<hash>]: label and a leading Revert " from each decision part that says reverted, keeping what is left when it has four or more characters (:131-142). A non-empty session whose decisions contain one of those phrases, or are contained in one, is skipped, and so is any phrase found inside one or containing one (:144-153, :166-169). The git hook writes a revert as Reverted / Superseded Decision [<hash>]: Revert "<subject>" (yantra_git.py:106-117), so the phrase is the reverted commit's subject, suppressed while the revert row is in the window.
  • Inbox. The scan reads Content, the Inbox sheet's text column, after Item and Raw Input (:158, core.py:2814-2816).

After promotion, a second pass over the same 50 sessions marks beliefs superseded (:288-324). For each reverted phrase it drops a leading always or never plus use or prefer, and any Beliefs row without Superseded_By whose Position contains the remainder, or is contained in the phrase, gets a supersede request keyed on its Topic, setting Superseded_By: Reverted in session log. The match is by substring over every belief, whoever wrote it, so reverting Always use tabs for indentation supersedes a belief reading Never use tabs for indentation as well. Every row sharing the Topic is marked.

Two promotions whose first 35 characters agree share a topic, and diff_beliefs groups rows by topic (core.py:866-896).

Promoted rows are not in the session context's principles section, which admits the Values and Constraints domains only (core.py:1960-1968); they reach semantic search, read_sheet, the HUD's recall, yantra context and the Sutra compiler, superseded or not.

The MCP sheet writes. add_inbox_item calls inbox with source Agent-observed; add_open_loop calls an alias of flush_open_loop; complete_task sets Status Done with source Agent-observed; and add_project passes its arguments by name (cognitive_mcp.py:401-460, core.py:757-779, :970-996). All six write as Cognitive-MCP, the agent name the server constructs OpenYantra with, and no tool argument names the requesting agent (cognitive_mcp.py:63). The iOS Shortcut server passes its default source, iOS Shortcut, to inbox, so the constructor's assert source in SOURCE refuses the write unless the request body names a valid source (ios_shortcut.py:66, :75, core.py:182-185).

Operational cost

Writes block the caller and are retrievable when the call returns, and each holds the workbook lock throughout, so writes from every process run one at a time. One sheet write parses the ledger sheet for its request id, then every other sheet, the target sheet and the ledger again, writes the whole workbook once, then rebuilds the search index: it reads eight sheets again, refits TF-IDF, re-encodes every row and rewrites the FAISS, BM25 and registry files. Each write's cost therefore grows with the whole workbook, and with MiniLM installed every write re-embeds the store. The yantra_sqlite.py docstring's 2 ms writes describe the unwired SQLite path.

Nidra reads the last 25 to 30 sessions per run with a ten-second Ollama timeout and runs only when asked. The OpenClaw adapter prepends the context block to the system prompt at session start, so any write since the last session changes the prompt prefix.

8. Agent Integration

The MCP server registers sixteen tools (cognitive_mcp.py:121-319). Five work on the JSON store: memory_write, memory_read, memory_search, memory_delete and memory_stats. Eleven work on the workbook: get_system_context, health_check, morning_brief, read_sheet, graph_traverse and six writes. The model names the agent on every memory_write, can delete any key including the agent-hierarchy-connections record behind the dashboard's agent hierarchy, and can read any sheet, the ledger and Quarantine included.

The adapters are thin. The LangChain chat history writes a session row on flush, and its retriever wraps search. The CrewAI memory routes save by kind and wraps search. The OpenClaw hooks inject the prompt block at session start, re-inject open loops after compaction and log a session at the end. The pre_compact_hook that its comment says preserves open loops returns the payload unchanged (adapters/openclaw.py:37-40). SKILL.md describes the library API for an agent and was read as data.

What the setup commands and installers write

  • yantra mcp setup writes mcpServers.openyantra into Claude Desktop's claude_desktop_config.json and ~/.cursor/mcp.json at their per-OS paths, pointing at the interpreter, the absolute path of cognitive_mcp.py and the workbook. It copies an existing file to .json.bak, replaces a file it cannot parse with a fresh one holding only its own entry, and creates both files whether or not the client is installed (mcp_setup.py:18-122).
  • yantra hook install writes .git/hooks/post-commit in the target repository, replacing any existing hook without a check. The hook runs python -m openyantra.cli hook run in the background with output discarded, against OPENYANTRA_FILE or a chitrapat.ods in the repository root (yantra_git.py:28-60, cli.py:23-24).
  • install.sh fetches forty files one at a time from raw…/main, continuing past any that fail. It installs Homebrew through its own curl | bash when Python is missing, runs sudo package installs on Linux, and pip-installs eleven unpinned packages into ~/openyantra/.venv. It writes the yantra launcher, a desktop shortcut whose quarantine attribute it strips, and PATH and OPENYANTRA_FILE lines appended to ~/.zshrc, ~/.bashrc or ~/.bash_profile (install.sh:21, :186-376).
  • install.ps1 does the same on Windows. It writes yantra.ps1, a yantra.bat that runs it with -ExecutionPolicy Bypass, a desktop shortcut, and the user-level PATH and OPENYANTRA_FILE variables.
  • The Dockerfile installs the core dependencies only and starts cognitive_mcp. Without faiss or a workbook inside the container, only the JSON memory tools work.

No installer registers a hook or an MCP config on its own; both need the commands above.

9. Reliability, Safety, and Trust

A refused write waits on its own lock

_process runs inside _workbook_lock, which opens .chitrapat.ods.lock and takes an exclusive portalocker lock (core.py:332-352, :368-369). A request that _validate rejects or _check_conflict refuses goes to _log_audit, which saves the ledger through _write_sheet, and _write_sheet opens the same lock file again on a new handle and asks for the same exclusive lock (:383-391, :596-615, :571-572). On POSIX, portalocker locks with fcntl.flock, which treats two handles as two owners even within one process, and the call blocks with no timeout. The request never returns. It holds the process's threading.Lock, so every later write from that process waits behind it, and the queue entry is never acknowledged, so the next constructor replays the request and blocks the same way (:323-326, :645-647).

Ordinary calls reach it: a write naming a Status or Priority outside the vocabulary, a write to an unknown sheet, or a Medium-confidence update to a field a High-confidence row holds. The MCP sheet tools and the adapters write at High, so the conflict case comes mostly from library and dashboard callers. I derived the block from the code and from flock itself, with a five-line script of my own that took the lock on one handle and was refused it on a second. I ran nothing from the repository. No test sends a rejected or conflicting write, and CI installs portalocker through .[full,dev].

Replay, the single save and the lock

LedgerAgent.submit appends each request to sanchitta.json, runs _process, and removes the entry by request id in a finally block, whether the write committed, was refused or raised (core.py:315-321, :280-286). The next OpenYantra constructor in any process empties the file and runs _process on whatever is in it (:645-647, :323-326). _process returns already_committed when the ledger sheet holds the request id (:354-366, :370-373). _commit_and_audit builds the target sheet and the ledger with the new written row and writes both, with every other sheet, to one temporary file that replaces the workbook (:453-569). A crash leaves either both or neither. The ledger check and the save run under the workbook lock, so a second process cannot replay a request between them.

Both guarantees hold only while the lock is taken. _workbook_lock catches any exception from opening or locking the file, logs it at debug level and runs the write unlocked (:338-343). An import failure has the same effect, and the queue lock does the same with its exceptions discarded (:242-262). Replay skips Raksha. A quarantined request never enters the queue, and a release submits a new request with a new id.

The gate covers one store of two

The single-writer design is real for the workbook and absent for the JSON store. CognitiveMemoryStore.write redacts secrets from the key and the content and asks Raksha to scan the content. A scan rating a confirmed or critical prompt injection raises ValueError, which the MCP server returns to the model as a tool error (cognitive_db.py:60-81, cognitive_mcp.py:94-102). When the import, the redaction or the scan raises anything else, four regexes for key-value secrets, sk-, ghp_ and AKIA keys stand in for the redaction, and no injection check runs. The block covers the prompt-injection type only, where the sheet path quarantines jailbreak, impersonation and encoding matches too, and a blocked note is refused rather than held for review.

The key is matched after redaction, so a key holding a secret updates its own note (:87-93). The store keeps no admission filter and writes no ledger row, and memory_delete removes the note with no trace (cognitive_mcp.py:330-366). memory_write redacts once more before calling the store, and the dashboard's POST /api/cognitive/write reaches the same store (yantra_ui.py:255-269). Raksha skips scanning entirely for the agent name User (yantra_security.py:475-483). The MCP sheet tools write as Cognitive-MCP, which has no registered tier and is scanned.

Concurrency and data loss

LedgerAgent holds a threading.Lock inside one process, and the workbook lock orders _process and _write_sheet across the MCP server, the dashboard, the bot, the hook and the CLI. Three writers read their sheet before the lock and write it under the lock: _quarantine, _log_security and archive_session_log. A sheet write landing between that read and that write is lost (core.py:1480-1500, :1502-1520, :1325-1370). A crash mid-write leaves the previous workbook whole. A sheet that fails to parse is written back empty, and a ledger that fails to parse is written back holding only the new row (:453-569). archive_session_log rewrites the Session Log directly, outside the ledger.

Declared and unwired

  • The SQLite engine. The README calls it the shared store; nothing outside tests calls SyncEngine.write, import_ods is a stub, and the dashboard's preference for SQLite reads is gated on the same mismatched map, so it reads the workbook (yantra_ui.py:166-187). export_ods would replace the workbook with the SQLite tables, which test_sync_wal_reconciliation shows; it fires only when SQLite's ledger has rows, and nothing writes them.
  • Edge inference. infer_edges is tested with lowercase keys and is never reached from request_write (section 4).
  • Ledger verification. Raksha.verify_mudra has no caller and hashes four keys where _seal hashes eleven, so it could not match a stored seal (yantra_security.py:345-360, core.py:446-448). yantra integrity checks only the sha256: prefix (core.py:1372-1421).
  • Corrections. propose_correction has no caller in the product, so the queue fills only from library code. The dashboard's review updates the Corrections row keyed on its target sheet, which marks every correction for that sheet with the same decision (yantra_ui.py:212-216). apply_corrections has no caller.

Capture channels open to others

The Telegram bot checks no sender. Anyone who messages it can add Inbox items, tasks, goals and loops and read open-loop topics and health counts (telegram_bot.py:97-240). The iOS Shortcut server binds 0.0.0.0:7332 with Access-Control-Allow-Origin: * and no token (ios_shortcut.py:81-83, :171). The mail daemon accepts any SMTP client on 127.0.0.1:2525. The dashboard has no authentication unless passkeys are enabled, and then only cookies from that process's memory count (yantra_ui.py:113-127).

Revert tracking

The git hook detects a revert by a subject starting with revert or a body containing reverts commit, and writes the Session Log row with a Reverted / Superseded Decision prefix and Status: REVERTED in the notes (yantra_git.py:106-117). Nidra's promotion scan skips that row and suppresses any phrase it contains, so a commit subject Always use tabs for indentation is not promoted while its revert is among the last 50 sessions. The reverted commit's own row is unchanged. A preference promoted before the revert is marked Superseded_By at the next consolidation run, and it leaves the session context's beliefs list. Search, read_sheet, yantra context, the Sutra compiler and the HUD's recall return it at High confidence, unmarked (section 6). Loop resolution reads revert rows, so a revert whose subject repeats an open loop's topic resolves that loop.

Marks

Three are earned; all apply to the sheet engine and none covers the JSON store.

  • audit_log — earned. The ledger sheet is appended for every request _process handles and written by nothing else: a written row in the same save as the change, a rejected or conflict row by _log_audit. Each row records who wrote to which sheet, when, with which operation, row identifier, confidence and source, and a hash of the request, and replay consults it before applying a request. The limits are real: an add names no row, no row carries the value, and on Linux and macOS a refusal's row never lands, because the request blocks on the lock first.
  • human_review — earned. A write matching a confirmed pattern waits in Quarantine, out of every sheet, the index and the context, until a person presses Release. No agent-facing surface carries a release verb, and the agent cannot write the Quarantine sheet. The dashboard does not show the held content, release does not close the item, and a released row is relabelled as the user's own statement at High confidence (core.py:1466-1470). The release route is a POST on 127.0.0.1 that needs no credential while passkeys are off, their default (yantra_ui.py:238-241, :777), so an agent with a general shell or HTTP tool can reach it; the mark rests on the declared tool surface carrying no release verb.
  • tombstone — withheld. No record keyed on a value refuses a later write. A superseded belief's Position stays in Nidra's known set, which keeps that phrase from being promoted again, but no other writer consults it, and a cognitive delete removes the note.
  • trust_state — withheld. Confidence is a four-value label. One context section admits only High beliefs, and the conflict guard protects High fields, but search, load_session_context, read_sheet and the prompt block return every level. Superseded_By on Beliefs does mean recorded but not believed, and only the session context's beliefs list, which nothing consumes, filters on it; search and both context compilers return the row.
  • bitemporal — withheld. No validity time exists beside Last Updated.
  • scope_enforced — withheld. The Agent column selects configured instructions, not memories. Every memory sheet, the index and the JSON store are shared by every agent.
  • negative_eval — earned. Two open loops are written and one resolved, and two tasks are written and one marked Done; load_session_context, the read behind MCP get_system_context, must return the live loop and the pending task and must not return the resolved loop or the Done task (tests/test_negative_eval.py:66-85, :88-114). A third case holds an injected task in Quarantine and asserts it is absent from the session context and the context markdown beside a real task that must be present (:18-63). Its search arm checks the positive control only when search returns something, so an empty index, which is what search gives without the search extras, passes both arms. The filtered-filler, reverted-decision and repeated-consolidation cases keep material out of a sheet or a promotion list, which are write decisions (:117-146, :149-183, :186-207). Search itself, which has no status filter, has no negative case.

What is not: no test sends a write that validation rejects or the conflict guard refuses, which is the path that blocks, and none exercises the release of a quarantined write, a request left in the queue and replayed by a constructor, or two processes. The idempotency tests call _process directly after the first write has finished, and the queue test constructs the second instance after the first has acknowledged. No test reads a superseded belief through search, yantra context or the Sutra compiler. The "error" not in resp checks cannot fail, because tool errors return inside result with isError (tests/test_cognitive.py:121, cognitive_mcp.py:94-102); the sheet-tool test also reads each sheet back, and that can. Importing cognitive_mcp at collection creates ~/openyantra/cognitive_memories.json in the real home directory and, if ~/openyantra/chitrapat.ods exists, opens it and replays its queue.

There is no retrieval-quality evaluation and no benchmark. WHITEPAPER.md is the project's paper, written at v2.10. Its validation section reports four rounds of review by eight language models with quoted verdicts, which is opinion rather than measurement, and it lists LOCOMO and DMR evaluation as not done. Its description of the write gates and trust tiers matches the code. It claims Mudra verification on read, which has no caller, and an incremental index sync, which is a full rebuild. No arXiv or DOI reference exists in the tree.

11. For Your Own Build

Steal

  • One choke point for every write, with a ledger row per outcome. Recording rejected and conflict beside written makes a refused write visible instead of silent. Write the ledger row in the same save as the change, as this one does for written, so a replay check can trust it. Give the ledger the row id and the value, which this one lacks.
  • A security hold the agent cannot drain. Put the release verb on a surface the agent has no tool for, keep the held write out of every sheet and index, and show the person what is held, not only why.
  • A store a person can open with a desktop application. A workbook with one sheet per kind of memory is legible without the product, which no database file is.

Avoid

  • A file lock taken again inside its own critical section. flock locks belong to the open handle, so a helper that opens the lock file and locks it waits forever when its caller already holds the lock. Take the lock once at the top and pass the locked state down, or use a reentrant wrapper, and send one refused write through the test suite.
  • A lock that degrades to nothing on error. Both locks log or discard any exception and run unlocked. Fail the write instead, since the replay guard relies on the lock.
  • A lifecycle column one reader filters. Superseded_By keeps a belief out of one context list and none of the others. Put the predicate in the shared sheet reader or evict the row from the index.
  • Two stores behind one name. If the agent's memory tools and the person's workbook are both "memory", put both behind the gate, or the model will use the ungated one.
  • Provenance set by the helper rather than the caller. A helper that stamps User-stated on every task turns the agent's writes into the person's statements.

Fit

This suits one person who wants to keep a hand-readable record of their own projects, people and open threads, edit it in LibreOffice, and hand a summary of it to a chat assistant. It is not ready as an agent's working memory. On Linux and macOS one rejected or conflicting write stops the writing process, and what the agent stores through the MCP memory tools never reaches its own context. The maintenance budget is a single author's, and the installer runs whatever main holds. Walk away if anything writes free-form status values, if anyone else can reach the Telegram bot, or if you need to delete anything.

12. Open Questions

  • Which store the author intends to be authoritative: the whitepaper's v3.0 plan makes the workbook the contract and SQLite the engine, and the code at the pin wires neither direction.
  • How often the Raksha patterns hold legitimate text in practice, and whether anyone uses the Release button.
  • Whether the superseded filter is meant for every context path or only the session context's beliefs list, which no caller reads.
  • Whether the MCP memory tools are meant to stay outside the ledger and the quarantine, given that the store refuses injections outright.
