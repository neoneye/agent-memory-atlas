On this page

1. Executive Summary

OpenYantra is a local, single-user memory toolkit that keeps a structured model of one person as sheets in a LibreOffice workbook, written through one gated writer and served to Claude Desktop and Cursor over MCP. The gate is the notable part: an injection scan that can hold a write for a person to release, an admission filter, vocabulary checks, and a row on an append-only ledger sheet.

A sheet change and its ledger row land in one atomic save, under a file lock that every process takes and that one thread can enter twice. When the lock call fails, the write runs under the thread lock alone. A belief marked superseded is left out of search and every context compiler by one shared predicate, and the gate refuses a later add or update that repeats its Topic or Position. The MCP memory tools and the dashboard write a separate JSON store with a secret filter, an injection block and a key tombstone, and no ledger.

Around that core sit a local OpenAI-compatible gateway that injects compiled context into chat requests and harvests decision phrases from both sides of the exchange, a git-file mesh that copies beliefs, tasks and projects between checkouts, a regex contradiction scan that can supersede beliefs, a source-comment scanner, a menu-bar tracker and a consolidation daemon. yantra proxy builds the gateway without a workbook, so that command forwards requests unchanged (section 8).

LICENSE is the MIT text; SPEC_LICENSE dedicates the protocol's table schemas, sheet templates and interchange formats to the public domain under CC0 1.0.

The README describes a SQLite WAL store shared by the HUD, the CLI and the MCP server. At this commit every write goes to the workbook. SQLite receives inferred graph edges after each write and a copy of ten sheets when yantra sync runs, and the dashboard and the HUD read their sheets from it: nothing before a sync, a stale copy after one, and an empty Quarantine, ledger and Corrections view at any time (section 6).

Four marks are earned, all on the sheet engine: audit_log on the ledger sheet, trust_state on the Beliefs sheet's Superseded_By, tombstone on the refusal that column drives, and negative_eval on a resolved loop, a Done task, a superseded belief and another project's task that the reads must leave out. human_review is withheld because the Release button sits behind that empty list. Section 9 gives the reason for each of the three withheld.

2. Mental Model

A memory is a row in a sheet of chitrapat.ods. The sheets are Identity, Goals, Projects, People, Preferences, Beliefs, Tasks, Open Loops, Session Log, Agent Config, the ledger (Agrasandhanī), Inbox and Corrections, plus Quarantine and Security Log created on first use. A row is identified by its first column — the attribute, task text or loop topic — and carries Confidence (High, Medium, Low, Inferred), Source (User-stated, Agent-observed, Agent-inferred, System), Importance 1 to 10 and Last Updated (openyantra/core.py:72-101, :2988-3084).

A row becomes a belief by passing five gates in order, and nothing marks it as less than true afterwards:

  • Raksha redacts secrets, then scans the joined field text. A confirmed injection, jailbreak, impersonation or zero-width pattern sends the write to Quarantine; a suspicious one adds a _security_flag column and lets it through (core.py:840-858, openyantra/yantra_security.py:496-594).
  • Admission drops a write whose content contains a noise phrase, whose content is at most two words including a filler word, or whose importance is below 2, with no ledger row (core.py:114-166).
  • Validation rejects an unknown sheet or a value outside the controlled vocabulary (core.py:485-500).
  • Tombstone rejects an add or update to Beliefs that repeats the Topic or Position of a superseded row (core.py:502-547).
  • Conflict refuses an update that would change a High-confidence field from a request that is not High (core.py:549-567).

A row stops counting through a lifecycle column read by the context builder: a loop resolved, a task Done, a project not Active, a goal not Active or In Progress (core.py:1346-1373). Identity, People and Preferences rows have no such column and change only by overwrite. Beliefs carry Superseded_By, which Nidra's revert pass and the drift resolver fill, and search and every context compiler drop a row that carries it (section 6). A delete request removes every row whose first column equals the identifier, compared trimmed and lowercased, and writes a written ledger row naming it; delete_row wraps the request and has callers only in tests (core.py:665-668, :1283-1314). A git revert adds a new Session Log row labelled Reverted / Superseded Decision; the reverted commit's own row is untouched (openyantra/yantra_git.py:106-127).

The cognitive store is a second memory with no relation to the first: a JSON list of notes with a key, a type, an agent name, content, tags and a timestamp. A write replaces the note with the same key case-insensitively, and a delete removes it (openyantra/cognitive_db.py:57-173). Only the MCP memory_* tools and the dashboard's cognitive routes reach it, and no context builder reads it.

Control is hybrid. The agent writes through MCP, a person writes through the HUD, the dashboard, the CLI, Telegram, LibreOffice or Obsidian, and Nidra resolves loops when someone runs it.

3. Architecture

Everything is one Python package, openyantra/, constructed per process. Each of the MCP server, the dashboard, the Telegram bot, the iOS Shortcut server, the mail daemon, the CLI and the git hook opens its own OpenYantra on the same workbook.

  • core.py holds OpenYantra, the writer LedgerAgent and the queue WriteQueue. The constructor replays the queue, opens the search index, and creates a SQLite SyncEngine beside the workbook (core.py:771-809).
  • yantra_security.py is Raksha: regex lists, secret redaction and trust tiers keyed on the writer's agent name.
  • vidyakosha.py is the search sidecar: a FAISS flat inner-product index, a pickled BM25 index and a JSON registry of indexed rows.
  • yantra_sqlite.py creates fifteen tables mirroring the sheets, plus _meta, _sync_state and edges, at every start (yantra_sqlite.py:158-411). In product code edges is written by the dashboard and by infer_edges after each committed write, and the sheet tables by import_ods alone.
  • cognitive_db.py and cognitive_mcp.py are the JSON store and a hand-written line-delimited JSON-RPC server announcing protocol 2024-11-05.
  • yantra_ui.py is a FastAPI app on 127.0.0.1:7331 serving UI/v4/dashboard.html and UI/v4/hud.html; desktop.py opens either in pywebview or a browser.
  • proxy.py is the gateway: a FastAPI app on 127.0.0.1:7332 serving /v1/chat/completions and forwarding to OPENYANTRA_UPSTREAM_URL, by default https://api.openai.com/v1, with the client's own headers (proxy.py:125-129, :245-249).
  • yantra_mesh.py, yantra_drift.py and yantra_anchors.py are the git-file mesh, the contradiction scan and the source-comment scanner.
  • menubar.py and workspace_detector.py are a tray icon that names the project in the frontmost editor's window title and offers a quick capture.

Beside the workbook the package keeps sanchitta.json, chitrapat.db, cognitive_memories.json, cognitive_memories_tombstones.json, settings.json, vidyakosha_centroids.json, vidyakosha.faiss, vidyakosha_bm25.pkl, vidyakosha_registry.json, a pratibimba/ folder of per-agent snapshots and yearly chitrapat_sessions_<year>.ods archives.

A write is a whole-file rewrite. The writer parses every sheet with pandas, writes them all to chitrapat.tmp.ods and moves it over the workbook with os.replace (core.py:580-701, :703-726). _workbook_lock takes a re-entrant lock on .chitrapat.ods.lock around the whole of _process and around _write_sheet, and the queue file takes one on sanchitta.lock around each load and save (:421-422, :350-351); section 9 describes the class. portalocker>=2.7 is a core dependency in pyproject.toml, install.sh and install.ps1, and the Dockerfile installs the package with pip install -e .. Both fall back to the thread lock alone when the import fails or the lock call raises (:64-68, :303-321).

Deployment and ergonomics

The core needs Python 3.9 or later with odfpy and pandas. Search adds scikit-learn and faiss-cpu, MiniLM is optional, and the dashboard adds FastAPI, uvicorn and webauthn. No API key is needed to store anything. For its summary sentence Nidra asks Apple's /usr/bin/fm command on macOS when its licence is accepted, then a local Ollama on localhost:11434, and falls back to a template (yantra_nidra.py:96-159). Everything runs offline except a gateway pointed at a remote upstream.

The store is the point of the design. A person can open chitrapat.ods in LibreOffice, read every sheet and fix a row by hand. Such an edit bypasses Raksha and the ledger. yantra sync calls SyncEngine.import_ods, which upserts ten sheets into the SQLite tables by first-column key and infers edges from each row; it removes nothing and writes no ledger row (yantra_sqlite.py:751-900, cli.py:443-445). A hand edit takes effect because the workbook is the store; the search index sees it at the next write, and the dashboard at the next sync.

The first-run path is curl … install.sh | bash or install.ps1; section 8 lists what each writes.

4. Essential Implementation Paths

  • Sheet write. OpenYantra.request_write (core.py:834-901) runs Raksha, then LedgerAgent.submit, which appends the request to sanchitta.json, calls _process, and removes the entry by request id in a finally block (:404-410, :369-375, :438-483). _process first returns already_committed for a request id the ledger sheet holds (:424-436), then runs admission, _validate, _check_tombstone, _check_conflict and _seal, and _commit_and_audit writes the sheet change and the written ledger row in one save; a rejection or conflict goes to _log_audit. On written, request_write calls VidyaKosha.sync over the whole workbook, because the incremental_update it checks for is not defined (:869-873). It then resolves the sheet to a SQLite table and calls infer_edges, which links a task, loop or goal to its project and any @Name to a known person; for a delete it removes the node's edges and its SQLite row instead (core.py:876-899, yantra_sqlite.py:1125-1170).
  • Replay. OpenYantra.__init__ calls replay_queue, which empties the queue and runs _process on every request in it (core.py:775-780, :412-415).
  • Capture. MCP sheet tools (cognitive_mcp.py:408-467); the dashboard and HUD through POST /api/inbox (yantra_ui.py:193-198, UI/v4/hud.html:425); yantra inbox (cli.py:379-382); Telegram commands and plain messages (telegram_bot.py:151-240); the iOS Shortcut server (ios_shortcut.py:55-93); the SMTP daemon (yantra_mail.py:20-49); Obsidian import (yantra_vault.py:181-245); the post-commit hook (yantra_git.py:63-127); and the CrewAI, LangChain and OpenClaw adapters. The gateway's harvest (proxy.py:360-386), the menu bar's quick capture, a Session Log row (menubar.py:238-242), and the mesh pull (yantra_mesh.py:350-479) write through the same gate.
  • Routing. route_inbox sends each unrouted Inbox row to the sheet a keyword list picks, as a Low-confidence Agent-inferred row, then marks the Inbox row by its full content (core.py:934-970, :2677-2698).
  • Consolidation. 5. Memory Data Model

The controlled vocabularies are sets in core.py:72-82: project, task and goal statuses, four priorities, Yes/No, three preference strengths, four confidence values, four sentiments, four sources and seven operations. Column names follow the template, and _commit_and_audit adds any new field as a new column, so a writer that names a field wrongly widens the sheet instead of failing.

Row identity is the first column's text. update, resolve, archive and supersede build a mask on the first column equal to row_identifier and change every matching row (core.py:614-663). An update that matches nothing appends a new row with the requested fields, so a mistyped task name sent to the dashboard's complete route creates a row with status Done and no task text.

Provenance is caller-supplied. Source and Added By come from the request. add_task, add_project and update_identity hardcode source="User-stated" and confidence="High", so a task the agent creates through MCP is recorded as the person's statement (core.py:1166-1206).

Scope. One workbook per person. The one key is the Agent Config sheet's Agent column, which load_session_context uses to pick the instructions an agent receives, with ALL as the wildcard; Tasks carry Project and Open Loops Related Project, which the session context filters on only when a caller names a project (section 6) (core.py:1339-1343). The cognitive notes carry an agent name that no read consults.

Time. Last Updated in UTC seconds, Opened on loops, Deadline on tasks and goals, and the ledger's request timestamp. There is no validity time. TTL_Days on loops is read by check_anishtha_ttl, which reports expired loops and changes nothing (core.py:1046-1075).

Belief columns. Beliefs carries Contradiction_Flag, written as No by Nidra's promotion and as Superseded by <successor> by a supersede, beside Superseded_By (core.py:648-663, :3037-3038). diff_beliefs returns same-topic groups to the CLI and the dashboard's insights (core.py:1014-1044, :2375, :2423-2430).

The SQLite schema mirrors the sheets with lowercase columns and a UNIQUE request id on ledger for idempotent writes (yantra_sqlite.py:158-411). SyncEngine.write has callers only in tests/test_setu.py; the tables fill from import_ods, which matches rows by first-column key and leaves ledger, session_log, corrections, quarantine and security_log untouched (yantra_sqlite.py:787-809).

Committed data files. The root chitrapat.ods is a workbook bootstrapped on 20 May 2026 at v2.12, holding a first name, a city and an occupation in Identity. Its Session Log has the bootstrap row twice, 15 seconds apart. Its ledger has the same four writes twice, under the same request ids and timestamps: the queue replay as it ran before e6a19a1, when nothing removed a processed entry, recorded in the project's own file. cognitive_memories.json is an empty list, and settings.json holds the defaults with empty key fields. .gitignore lists all three as user data. openyantra/chitrapat_template.ods is the blank template.

6. Retrieval Mechanics

Context injection is assembled from sheets, not search. load_session_context returns the identity map, the agent's instructions, Active projects, unresolved loops sorted by importance and capped at 15, Active or In Progress goals, tasks whose status is not Done, pending corrections, the unrouted Inbox count and the Beliefs rows that are not superseded (core.py:1335-1405). Archived and Blocked tasks pass that filter. No other code reads the beliefs list.

is_superseded counts a row as superseded when Superseded_By holds anything but an empty or null-like value, when Contradiction_Flag starts with superseded, or when Status is Superseded or Reverted (core.py:189-214). build_context_markdown caps each section at four to eight items and adds Values and Constraints beliefsto eight items and adds Values and Constraints beliefs at High confidence that are not superseded, the first five People rows and Strong preferences (core.py:2112-2274). It is the only reader that uses Confidence to exclude a row. yantra context takes the first five beliefs of importance 7 or more that are not superseded (yantra_context.py:149-159), and SutraCompiler filters projects, loops, goals and tasks by status and Beliefs by the same predicate (yantra_sutra.py:248-264).

Project scope is a per-call option. load_session_context takes a project_scope. With one, it keeps Projects whose name contains the scope, and Tasks and Open Loops whose Project or Related Project contains it or is empty; without one, or with all, it filters nothing (core.py:1346-1384). Goals, Beliefs, People and Preferences are returned whole either way. build_context_markdown, the Sutra compiler and yantra context --project pass the scope through (core.py:2131, yantra_sutra.py:266-274, yantra_context.py:261). MCP get_system_context reads a project argument that its tool schema does not declare (cognitive_mcp.py:187-196, :381-383), and the gateway takes an X-Project-Scope header or, failing that, OPENYANTRA_PROJECT or the name of the git repository enclosing the server's own working directory (proxy.py:216, core.py:169-186). The match is a lowercase substring, so a scope of app admits AppAlpha and AppBeta. Search, read_sheet and the JSON store take no scope.

Routing. route scores a prompt against the mean vector of each indexed sheet and returns the two closest; with auto_route, the Sutra compiler keeps identity, instructions and the sections for those sheets (vidyakosha.py:508-546, yantra_sutra.py:96-105). The gateway and yantra route are its callers. "Zero retention" in the docstring means the prompt is not written to the index (core.py:1547-1557).

Two reads of the workbook apply no supersession filter. MCP read_sheet returns the sheet's rows with their Superseded_By column (cognitive_mcp.py:398-406). The terminal and Telegram morning brief and the digest each draw a past memory from Goals and Beliefs (core.py:2033-2052, yantra_digest.py:201-203, yantra_morning.py:127-131); the MCP morning_brief tool asks for markdown, which omits that line.

The dashboard and the HUD read SQLite. GET /api/sheet/{name} looks the sheet's name up in SHEET_TABLE_MAP, which holds every sheet under its emoji name, and returns db_engine.read(table) without opening the workbook (yantra_ui.py:157-190, yantra_sqlite.py:61-93, :558-570). No write path fills those tables: yantra sync copies ten sheets, and ledger, session_log, corrections, quarantine and security_log have no writer outside tests. The dashboard's project, task, loop and inbox views and the HUD's recall therefore show the state of the last sync, and its ledger, Corrections and Security views show nothing; the Security view prints "No quarantined writes -- Chitrapat is clean" over a Quarantine sheet that holds rows (UI/v4/dashboard.html:878-884). No test requests the route.

Semantic search indexes eight sheets: Identity, Goals, Projects, People, Preferences, Beliefs, Tasks and Open Loops (vidyakosha.py:237-240). Each row becomes [sheet] column: value … without the confidence, source and date columns. The vector arm is FAISS IndexFlatIP over TF-IDF with truncated SVD, or MiniLM when installed; BM25 runs at k1 1.5 and b 0.75. Each arm is normalised by its maximum and fused at 0.7 vector to 0.3 BM25, and OpenYantra.search then multiplies by importance and a one-year recency ramp (vidyakosha.py:368-461, core.py:1479-1536). A superseded belief is skipped while the fused list is cut to top_k, and OpenYantra.search filters again unless the caller passes include_superseded, which no caller does (vidyakosha.py:445-459, core.py:1505-1510). No other status filter applies, so a resolved loop, a Done task and a Cancelled project rank like live ones. The index row carries the sheet row as it stood at the last rebuild, which every committed write triggers.

A per-agent snapshot freezes the registry at session start and keeps querying the live FAISS and BM25 indexes, so positions in a rebuilt index can address a different row of the frozen registry (vidyakosha.py:463-477, :565-575).

The HUD's recall fetches /api/sheet/beliefs and filters it by substring in the browser (UI/v4/hud.html:450-462). MCP memory_search is a substring match over key and content with type, all-tags and date-prefix filters, and returns every match. graph_traverse is a recursive CTE walking edges both ways for up to six hops, with a path-substring cycle guard.

The MCP server injects nothing on its own; the model has to call get_system_context. The gateway does inject: it compiles a context for the last user turn and appends it to the system message inside <yantra_memory> tags (proxy.py:71-95, :222-231). Cognitive notes are never part of any context.

7. Write Mechanics

No model extracts or rewrites memory; Nidra's model call produces only the summary sentence it logs as a session. Every write is an explicit call except the gateway's harvest.

Admission drops short filler. _is_worth_remembering joins the content fields, leaving out importance, confidence, priority, status, source, author, date and deadline. It drops the write when that text contains one of six phrases such as user said thanks, or when it is at most two words and one of them is a filler word such as sure, noted or great (core.py:114-166). "Make sure the backup runs" is admitted; "Sure thing" is dropped with status filtered and no ledger row. The filler set lists thank you and got it as entries, and a single word never equals either. Session Log, Inbox and Corrections writes skip the filter.

A superseded belief refuses its own value. On an add or update to Beliefs, _check_tombstone reads the sheet and returns rejected when a superseded row has the same Position or the same Topic as the request, trimmed and lowercased, and _process writes the refusal to the ledger (core.py:459-462, :502-547). The record is the superseded row itself. The Topic arm closes the whole topic: once a belief under ORM Choice is superseded, its replacement needs another Topic. Four things lift the refusal:

  • a field named allow_override, override_tombstone, Override_Tombstone or allow_superseded_override set true in the request, which no product caller sends and which an add then stores as a column (:511-518);
  • a delete of the superseded row;
  • wording that differs by a character;
  • any exception inside the check, which is logged at debug level and admits the write (:545-547).

The gateway harvests both sides of a chat. After a response, two regexes run over User: … Assistant: … and keep the text after phrases such as we will, decided to, switching to and rule: (proxy.py:34-37, :360-373). Up to three matches go to the Session Log's decisions through log_session, which writes them as System at High confidence under the agent name Agent (proxy.py:379-383, core.py:1153-1164). Raksha and the ledger apply. Model output is stored beside the person's own statements with nothing but a Notes string to tell them apart, and Nidra's promotion scan reads those decisions for preference phrases.

The mesh copies rows between checkouts. push overwrites .openyantra/mesh/mesh.jsonl with every belief that is not superseded, Active projects, pending tasks and the decisions of the last 30 sessions, then runs git add and git commit; no remote is contacted (yantra_mesh.py:229-338). pull reads that file from the working tree (:350-479):

  • A belief whose Topic is absent locally is added as User-stated at High confidence under the agent name MeshSync (<author>), where the author is the exporting row's Source cell (:410-431). An inferred belief on one machine is the person's own statement on the next.
  • A belief whose Topic exists with another Position becomes a Pending Corrections row (:386-408); tasks and projects match by name and are never updated.
  • The exported signature is a hash of topic, content and author that no code compares on the way in.
  • The write's receipt is ignored, so a refused or quarantined row counts as merged.

A superseded belief is not exported, so a supersession does not travel, and the tombstone check keeps the local row superseded. A deleted row comes back: sync pulls before it pushes, the file still holds the row, and nothing records the deletion.

Drift resolution supersedes beliefs. DriftEngine.analyze compares beliefs that are not superseded with recent session decisions and active tasks by three hardcoded invariants, eleven opposing regex pairs and a numeric budget rule, and writes nothing (yantra_drift.py:358-612). resolve_contradiction sends a supersede for the belief, a Session Log revert row or a Pending Corrections row, as VicharaResolver and User-stated (:614-701). yantra resolve --auto supersedes the belief on every direct negation or budget violation with no person in the loop, and the dashboard's POST /api/drift/resolve does the same by list index (cli.py:848-860, yantra_ui.py:834-866).

**Conflict detection is a refusal with nowhere to go.**Conflict detection is a refusal with nowhere to go. A conflicting update returns resolution: pending_user; the requested value is kept only as text in the ledger row's reason (core.py:464-472). Most MCP and adapter writes are High confidence, so the guard rarely fires.

Duplicates are made, not removed.

  • When the workbook lock is not taken, a second process replaying the queue while the first is inside _process applies the request again; an add lands a second row (section 9).
  • Obsidian import reads every line of Inbox.md again on each sync and never clears the file (yantra_vault.py:232-245).

Nidra. prune_and_resolve_loops resolves an open loop when its topic, or its first three words of four or more letters, appears in the decisions and topics of the last 30 sessions (yantra_nidra.py:324-376). Revert rows are part of that corpus. detect_promotable_preferences scans the last 30 sessions and 20 Inbox rows for phrases such as user prefers, always use and never prefer (yantra_nidra.py:237-322). Each new match longer than eight characters becomes a Beliefs row with Topic Pref: <first 35 characters>, Position User Preference: <phrase>, Confidence High, Source Agent-inferred and Importance 8, written through request_write as NidraConsolidator with the topic as its row identifier (:306-315, :389-419). The phrase is the text after the trigger, so never use tabs for indentation and always use tabs for indentation both become User Preference: tabs for indentation. Three checks sit in front of it:

  • Already stored. The known set holds each stored Position, the same Position without its User Preference: prefix, and each Topic, and a phrase promoted in this run joins it (:244-253, :316-319). A second run adds nothing, and a superseded row keeps its phrase out.
  • Reverted. A pre-pass over the last 50 sessions strips the Reverted / Superseded Decision [<hash>]: label and a leading Revert " from each decision part that says reverted, keeping what is left when it has four or more characters (:264-275). A non-empty session whose decisions contain one of those phrases, or are contained in one, is skipped, and so is any phrase found inside one or containing one (:277-286, :299-302). The git hook writes a revert as Reverted / Superseded Decision [<hash>]: Revert "<subject>" (yantra_git.py:106-117), so the phrase is the reverted commit's subject, suppressed while the revert row is in the window.
  • Inbox. The scan reads Content, the Inbox sheet's text column, after Item and Raw Input (yantra_nidra.py:291, core.py:3068-3070).

After promotion, a second pass over the same 50 sessions marks beliefs superseded (yantra_nidra.py:421-457). For each reverted phrase it drops a leading always or never plus use or prefer, and any Beliefs row without Superseded_By whose Position contains the remainder, or is contained in the phrase, gets a supersede request keyed on its Topic, setting Superseded_By: Reverted in session log. The match is by substring over every belief, whoever wrote it, so reverting Always use tabs for indentation supersedes a belief reading Never use tabs for indentation as well. Every row sharing the Topic is marked.

Two promotions whose first 35 characters agree share a topic, and diff_beliefs groups rows that are not superseded by topic (core.py:1014-1044).

Promoted rows are not in the session context's principles section, which admits the Values and Constraints domains only (core.py:2208-2219); they reach semantic search, read_sheet, yantra context and the Sutra compiler until a revert supersedes them.

The MCP sheet writes. add_inbox_item calls inbox with source Agent-observed; add_open_loop calls an alias of flush_open_loop; complete_task sets Status Done with source Agent-observed; and add_project passes its arguments by name (cognitive_mcp.py:408-467, core.py:905-927, :1118-1144). All six write as Cognitive-MCP, the agent name the server constructs OpenYantra with, and no tool argument names the requesting agent (cognitive_mcp.py:63). The iOS Shortcut server passes its default source, iOS Shortcut, to inbox, so the constructor's assert source in SOURCE refuses the write unless the request body names a valid source (ios_shortcut.py:66, :75, core.py:229-232).

Operational cost

Writes block the caller and are retrievable when the call returns, and each holds the workbook lock throughout, so writes from every process run one at a time. One sheet write parses the ledger sheet for its request id, the Beliefs sheet again when that is its target, then every other sheet, the target sheet and the ledger again, writes the whole workbook once, then rebuilds the search index: it reads eight sheets again, refits TF-IDF, re-encodes every row and rewrites the FAISS, BM25 and registry files. Each write's cost therefore grows with the whole workbook, and with MiniLM installed every write re-embeds the store. The yantra_sqlite.py docstring's 2 ms writes describe SyncEngine.write, which no product code calls.

Nidra reads the last 25 to 30 sessions per run with a ten-second Ollama timeout or a five-second Apple model timeout, then runs the drift scan; it runs when asked or when the daemon finds the workbook idle. The OpenClaw adapter prepends the context block to the system prompt at session start, so any write since the last session changes the prompt prefix.

8. Agent Integration

The MCP server registers sixteen tools (cognitive_mcp.py:121-319). Five work on the JSON store: memory_write, memory_read, memory_search, memory_delete and memory_stats. Eleven work on the workbook: get_system_context, health_check, morning_brief, read_sheet, graph_traverse and six writes. The model names the agent on every memory_write, can delete any key including the agent-hierarchy-connections record behind the dashboard's agent hierarchy, and can read any sheet, the ledger and Quarantine included. Four arguments the handlers read are in no tool schema: project and top_k on get_system_context, override_tombstone on memory_write and tombstone on memory_delete (cognitive_mcp.py:187-196, :336, :369, :381-382).

The adapters are thin. The LangChain chat history writes a session row on flush, and its retriever wraps search. The CrewAI memory routes save by kind and wraps search. The OpenClaw hooks inject the prompt block at session start, re-inject open loops after compaction and log a session at the end. The pre_compact_hook that its comment says preserves open loops returns the payload unchanged (adapters/openclaw.py:37-40). SKILL.md describes the library API for an agent and was read as data.

9. Reliability, Safety, and Trust

The workbook lock

Both file locks are one class, _ReentrantFileLock, keyed on the resolved lock path in a process-wide registry. Each path holds a threading.RLock, a depth count and the open file. The first entry in a process takes the RLock, opens the lock file and takes an exclusive portalocker lock; a nested entry by the same thread takes the RLock again and raises the depth, and the file lock is released when the depth returns to zero (core.py:280-338). Threads in one process wait on the RLock, and processes wait on the file lock.

_process runs inside _workbook_lock (core.py:421-422, :438-439). A request that _validate rejects or _check_conflict refuses goes to _log_audit, which saves the ledger through _write_sheet, and _write_sheet enters the same lock again (:454-467, :728-747, :703-704). The nested entry finds the depth above zero, so the rejected or conflict row is saved and the request returns. A write naming a Status or Priority outside the vocabulary, a write to an unknown sheet, or a Medium-confidence update to a field a High-confidence row holds each end there. The first two have a test that reads the rejected row back (tests/test_posix_lock_and_lineage_filtering.py:40-108); the conflict path has none. I ran nothing from the repository.

Replay, the single save and the lock

LedgerAgent.submit appends each request to sanchitta.json, runs _process, and removes the entry by request id in a finally block, whether the write committed, was refused or raised (core.py:404-410, :369-375). The next OpenYantra constructor in any process empties the file and runs _process on whatever is in it (:777-779, :412-415). _process returns already_committed when the ledger sheet holds the request id (:424-436, :440-443). _commit_and_audit builds the target sheet and the ledger with the new written row and writes both, with every other sheet, to one temporary file that replaces the workbook (:580-701). A crash leaves either both or neither. The ledger check and the save run under the workbook lock, so a second process cannot replay a request between them.

Both guarantees hold across processes only while the file lock is taken. The lock class catches any exception from opening or locking the file, logs it at debug level and carries on under the thread lock alone (core.py:303-321), and an import failure has the same effect; the queue lock is the same class. Replay skips Raksha. A quarantined request never enters the queue, and a release submits a new request with a new id.

The gate covers one store of two

The single-writer design is real for the workbook and absent for the JSON store. CognitiveMemoryStore.write redacts secrets from the key and the content and asks Raksha to scan the content. A scan rating a confirmed or critical prompt injection raises ValueError, which the MCP server returns to the model as a tool error (cognitive_db.py:78-99, cognitive_mcp.py:94-102). When the import, the redaction or the scan raises anything else, four regexes for key-value secrets, sk-, ghp_ and AKIA keys stand in for the redaction, and no injection check runs. The block covers the prompt-injection type only, where the sheet path quarantines jailbreak, impersonation and encoding matches too, and a blocked note is refused rather than held for review.

The key is matched after redaction, so a key holding a secret updates its own note (cognitive_db.py:117-123). The store keeps no admission filter and writes no ledger row. memory_delete removes the note and records its key and the time in cognitive_memories_tombstones.json; a later write to that key raises unless it passes override_tombstone, and the model can send that argument, or tombstone: false on the delete (cognitive_db.py:101-112, :152-173, cognitive_mcp.py:330-371). memory_write redacts once more before calling the store, and the dashboard's POST /api/cognitive/write reaches the same store (yantra_ui.py:255-269). Raksha skips scanning entirely for the agent name User (yantra_security.py:514-522). The MCP sheet tools write as Cognitive-MCP, which has no registered tier and is scanned.

Concurrency and data loss

LedgerAgent holds a threading.RLock inside one process, and the workbook lock orders _process and _write_sheet across the MCP server, the dashboard, the bot, the hook and the CLI. Three writers read their sheet before the lock and write it under the lock: _quarantine, _log_security and archive_session_log. A sheet write landing between that read and that write is lost (core.py:1726-1746, :1748-1766, :1571-1616). A crash mid-write leaves the previous workbook whole. A sheet that fails to parse is written back empty, and a ledger that fails to parse is written back holding only the new row (:580-701). archive_session_log rewrites the Session Log directly, outside the ledger.

Declared and unwired

  • The SQLite engine. The README calls it the shared store. Nothing outside tests calls SyncEngine.write, the sheet tables fill only from yantra sync, and the dashboard reads them (section 6). export_ods would replace the workbook with the SQLite tables, which test_sync_wal_reconciliation shows; reconcile, which the daemon calls after each consolidation, fires it only when SQLite's ledger has rows, and nothing writes them (yantra_sqlite.py:449-471, yantra_nidra.py:607-611).
  • Deletion. delete_row has callers only in tests, so no CLI command, MCP tool or dashboard route deletes a sheet row (core.py:1283-1314).
  • Ledger verification. LedgerAgent.verify_mudra recomputes a request's seal and has callers only in tests; a ledger row stores no fields, so a seal cannot be recomputed from the workbook (core.py:569-575, :1316-1318). yantra integrity checks that a signature is sha256: and 32 hex characters (yantra_security.py:433-438).
  • Corrections. The mesh pull and the drift resolver add Pending rows to Corrections; propose_correction has no caller. The dashboard's review list reads the unfilled SQLite table, its review route updates the Corrections row keyed on its target sheet, which marks every correction for that sheet with the same decision (yantra_ui.py:212-216), and apply_corrections has no caller, so an approved correction changes nothing.
  • Anchor drift. The drift scan's check for anchors that point at superseded beliefs reads anchors the scanner has not linked, whose status is always unknown, and two of the actions it proposes, cancel_task and update_anchor, return unsupported_action (yantra_drift.py:424-427, :556-585, :699-701).

Capture channels open to others

The Telegram bot checks no sender. Anyone who messages it can add Inbox items, tasks, goals and loops and read open-loop topics and health counts (telegram_bot.py:97-240). The iOS Shortcut server binds 0.0.0.0:7332 with Access-Control-Allow-Origin: * and no token (ios_shortcut.py:81-83, :171). The mail daemon accepts any SMTP client on 127.0.0.1:2525, and the gateway any HTTP client on 127.0.0.1:7332, or on whatever --host names. The dashboard has no authentication unless passkeys are enabled, and then only cookies from that process's memory count (yantra_ui.py:113-127).

Revert tracking

The git hook detects a revert by a subject starting with revert or a body containing reverts commit, and writes the Session Log row with a Reverted / Superseded Decision prefix and Status: REVERTED in the notes (yantra_git.py:106-117). Nidra's promotion scan skips that row and suppresses any phrase it contains, so a commit subject Always use tabs for indentation is not promoted while its revert is among the last 50 sessions. The reverted commit's own row is unchanged. A preference promoted before the revert is marked Superseded_By at the next consolidation run, and search and every context compiler then leave it out. read_sheet returns it with the column, and the morning brief shows it unmarked (section 6). Loop resolution reads revert rows, so a revert whose subject repeats an open loop's topic resolves that loop.

Marks

Four are earned; all apply to the sheet engine and none covers the JSON store.

  • audit_log — earned. The ledger sheet is appended for every request _process handles and written by nothing else: a written row in the same save as the change, a rejected or conflict row by _log_audit. Each row records who wrote to which sheet, when, with which operation, row identifier, confidence and source, and a hash of the request, and replay consults it before applying a request. A delete and a tombstone refusal each leave their row. The limits are real: an add names no row, and no row carries the value, so the ledger says that a row was deleted and not what it held.

  • human_review — withheld. A write matching a confirmed pattern waits in Quarantine, out of every sheet, the index and the context, and no agent-facing surface carries a release verb. The one caller of the release route is the dashboard's Release button, drawn once per row of /api/sheet/quarantine, and that route returns the SQLite quarantine table, which no code fills (section 6). The dashboard reports a clean store and draws no button, so the queue has no drain in the running product. A person who knows a request id can POST it to /api/security/quarantine/release (yantra_ui.py:238-241, UI/v4/dashboard.html:1090-1093), and a released row is relabelled as the user's own statement at High confidence.

  • tombstone — earned. A superseded Beliefs row is a durable record that the gate matches by value: an add or update repeating its Position or Topic is rejected whatever agent sends it and whatever Topic it is filed under, and the refusal is ledgered (core.py:502-547). Nidra's promotion and the mesh import both pass through it. Section 7 lists what lifts it: an override field any request can carry, a delete of the row, a paraphrase, and an exception inside the check. The JSON store's tombstone is keyed on a note's key, so the same content under another key is accepted.

  • trust_state — earned. Superseded_By on Beliefs means recorded but not believed. supersede requests write it, from Nidra's revert pass and the drift resolver, and one predicate, is_superseded, drops the row from search, from the session context, from build_context_markdown, yantra context and the Sutra compiler, and from diff_beliefs, the drift scan and the mesh export (core.py:189-214, :648-663, yantra_nidra.py:435-457). The state covers Beliefs only. MCP read_sheet returns the row with its column, and the morning brief and the digest show its Position to the person unmarked. Confidence is a four-value label that one context section and the conflict guard use; search and the other reads return every level.

  • bitemporal — withheld. No validity time exists beside Last Updated.

  • scope_enforced — withheld. The project filter is real and tested, and it is an option a caller may leave out: with no project_scope the session context returns every project's tasks and loops, the declared get_system_context tool has no argument for one, and the gateway falls back to the server's own working directory (section 6). It matches by substring and leaves Goals, Beliefs, search and read_sheet unfiltered. The Agent column selects configured instructions, not memories, and the JSON store is shared by every agent.

  • negative_eval — earned. Two open loops are written and one resolved, and two tasks are written and one marked Done; load_session_context, the read behind MCP get_system_context, must return the live loop and the pending task and must not return the resolved loop or the Done task (tests/test_negative_eval.py:65-84, :87-113). A third case holds an injected task in Quarantine and asserts it is absent from the session context and the context markdown beside a real task that must be present (:17-62).

    A superseded belief must be absent from search, both context compilers, the Sutra compiler and the session context while a live belief on the same topic is present, and this search arm checks its positive control unconditionally (tests/test_posix_lock_and_lineage_filtering.py:111-245). The search arm in tests/test_negative_eval.py checks its control only when search returns something.

    Tasks and loops written under two projects must each be absent from the other project's session context, context markdown and get_system_context result, while the project's own task and a task with no project are present (tests/test_workspace_isolation.py:20-156).

    The filtered-filler, reverted-decision and repeated-consolidation cases keep material out of a sheet or a promotion list, which are write decisions (tests/test_negative_eval.py:116-145, :148-182, :185-206). Search has no status filter for loops, tasks or projects and no case for them.

What is not:

  • None requests /api/sheet/{name}, so the dashboard's read of SQLite is unasserted in either direction.
  • The scoped cases pass a full project name; none passes a scope that is a substring of two names, and none scopes search.
  • The gateway cases assert that a memory block is present and never that another project's row or a superseded belief is absent from it; none runs yantra proxy.
  • The mesh cases hold no superseded, deleted or quarantined row and no altered signature, and none reads the Source or Confidence of an imported belief.

The idempotency tests call _process directly after the first write has finished, and the queue test constructs the second instance after the first has acknowledged. The superseded rows that search and the compilers are tested on are written by an add that sets Superseded_By and Status itself; the cases that mark a belief by a supersede request or Nidra's revert pass read only the session context's beliefs list. There is no retrieval-quality evaluation and no benchmark. WHITEPAPER.md is the project's paper, written at v2.10. Its validation section reports four rounds of review by eight language models with quoted verdicts, which is opinion rather than measurement, and it lists LOCOMO and DMR evaluation as not done. Its description of the write gates and trust tiers matches the code. It claims Mudra verification on read, which has no caller, and an incremental index sync, which is a full rebuild. No arXiv or DOI reference exists in the tree.

11. For Your Own Build

Steal

  • One choke point for every write, with a ledger row per outcome. Recording rejected and conflict beside written makes a refused write visible instead of silent. Write the ledger row in the same save as the change, as this one does for written, so a replay check can trust it. Give the ledger the row id and the value, which this one lacks.
  • A superseded row that refuses its own value. Matching a new write against the Position of every superseded row turns a status column into a refusal that re-extraction cannot walk past. Keep the override off the request: a field any writer can set is --force.
  • A security hold the agent cannot drain. Put the release verb on a surface the agent has no tool for, keep the held write out of every sheet and index, and show the person what is held, not only why. Test that the list is populated; this one is not.
  • A store a person can open with a desktop application. A workbook with one sheet per kind of memory is legible without the product, which no database file is.

Avoid

  • A read path switched to a cache nothing fills. Widening one lookup map so that edge inference could find its table also sent every dashboard read to SQLite, which only a manual sync populates. A cache needs a writer on the write path or a fallback on a miss, and a test that requests the route.
  • A sync that re-imports what was deleted. The mesh pulls before it pushes, from a file that still holds the row, and nothing records the deletion. Export a deletion marker, or do not offer delete beside sync.
  • An import that upgrades provenance. Stamping every incoming belief User-stated and High makes a teammate's inferred row the local person's own statement.
  • A lock that degrades to a thread lock on error.- A lock that degrades to a thread lock on error. Both file locks log any exception from opening or locking the file at debug level and carry on under the thread lock alone, which orders nothing across processes. Fail the write instead, since the replay guard relies on the file lock.
  • A test named for a path it does not reach. The case named for a conflicting write sends a Status outside the vocabulary and asserts rejected, so the conflict guard's refusal has no test. Assert the outcome the name promises.
  • Two stores behind one name. If the agent's memory tools and the person's workbook are both "memory", put both behind the gate, or the model will use the ungated one.
  • Provenance set by the helper rather than the caller. A helper that stamps User-stated on every task turns the agent's writes into the person's statements.

Fit

This suits one person who wants to keep a hand-readable record of their own projects, people and open threads, edit it in LibreOffice, and hand a summary of it to a chat assistant. It is not ready as an agent's working memory: what the agent stores through the MCP memory tools never reaches its own context. The maintenance budget is a single author's, and the installer runs whatever main holds. Walk away if anyone else can reach the Telegram bot, if you rely on the dashboard to show what is stored or held, or if you plan to share a workbook through the mesh.

12. Open Questions

  • Which store the author intends to be authoritative: the whitepaper's v3.0 plan makes the workbook the contract and SQLite the engine, and the code at the pin writes the workbook and reads the dashboard from SQLite.
  • How often the Raksha patterns hold legitimate text in practice.
  • Whether read_sheet and the morning brief are meant to show superseded beliefs, which every compiler and search leave out.
  • Whether the tombstone's Topic arm is meant to close a topic to its own successor.
  • Whether the mesh is meant to carry supersessions and deletions, which it drops.
  • Whether the MCP memory tools are meant to stay outside the ledger and the quarantine, given that the store refuses injections outright.
